Часть I

Механика: как Compose устроен внутри

Девять разделов подряд, читать по порядку. К концу будет понятно, почему функция перезапускается, что при этом происходит с памятью и какие решения из этого следуют. Кейсы во второй части ссылаются на разделы по номерам.

01 Идея: UI описывается заново, а не правится по месту

В XML-подходе разметка создается один раз, а дальше правится императивно: нашли вьюху, присвоили текст, спрятали, показали. Экран — это объект, который живет и меняется.

// как это выглядит на View
binding.textViewName.text = user.name
binding.imageViewAvatar.isVisible = user.avatarUrl != null
binding.buttonSubscribe.isEnabled = !user.isSubscribed

В Compose нет объекта-вьюхи, которому можно что-то присвоить. Есть функция, которая по текущим данным описывает, как экран должен выглядеть, — и Compose вызывает ее заново, когда данные изменились.

@Composable
fun UserHeader(user: User, onSubscribe: () -> Unit) {
    Row(verticalAlignment = Alignment.CenterVertically) {
        if (user.avatarUrl != null) {
            AsyncImage(model = user.avatarUrl, contentDescription = null)
        }
        Text(text = user.name)
        Button(onClick = onSubscribe, enabled = !user.isSubscribed) {
            Text(text = "Подписаться")
        }
    }
}

Отсюда главное следствие: у функции нет «текущего состояния экрана», которое можно поправить. Все, что должно отличаться между прогонами, обязано приехать снаружи — либо параметром, либо из состояния, за которым Compose следит. Дальше разберемся, что такое «следит».

композиция
Первый прогон composable-функций. Compose выполнил их сверху вниз и получил дерево того, что показать на экране.
рекомпозиция
Повторный прогон части этих функций, когда данные изменились. Не перерисовка всего экрана, а перевыполнение отдельных функций.
состояние (state)
Значение, за изменением которого Compose следит: MutableState. Обычная переменная состоянием не является.
группа
Кусок кода, для которого рантайм хранит отдельную запись в памяти композиции: тело функции, ветка if, элемент списка.

02 Состояние: почему обычной переменной не хватает

Самый показательный эксперимент — счетчик в четырех вариантах. Разница между ними ровно в двух словах: remember и mutableStateOf.

Вариант 1 — обычная переменная

@Composable
fun Counter() {
    var count = 0                                   // ни памяти, ни наблюдения

    Button(onClick = { count++ }) {
        Text(text = "Нажато $count раз")
    }
}

Экран не меняется вообще. count++ отрабатывает, но Compose про это изменение не знает — рекомпозиции нет, а если бы и была, переменная создалась бы заново с нулем.

Вариант 2 — есть память, нет наблюдения

var count = remember { 0 }                          // значение переживет прогон
Button(onClick = { count++ }) { … }                 // но об изменении никто не узнает

То же самое на экране: ноль. remember дает память, но не уведомление.

Вариант 3 — есть наблюдение, нет памяти

var count by mutableStateOf(0)                      // без remember
Button(onClick = { count++ }) { … }

Значение изменилось, рекомпозиция запустилась — и создала новое состояние с нулем. Счетчик мигает единицей и возвращается к нулю. Lint ловит это проверкой UnrememberedMutableState с уровнем Error.

Вариант 4 — правильно

@Composable
fun Counter() {
    var count by remember { mutableIntStateOf(0) }

    Button(onClick = { count++ }) {
        Text(text = "Нажато $count раз")
    }
}
ВариантПамять между прогонамиCompose узнает об измененииЧто на экране
var count = 0нетнетвсегда 0
remember { 0 }естьнетвсегда 0
mutableStateOf(0)нетестьмигает и сбрасывается
remember { mutableIntStateOf(0) }естьестьсчитает

Два слова отвечают за две разные вещи: remember — «сохрани между прогонами», mutableStateOf — «следи за изменениями». Нужны оба, и это не дублирование.

03 Что дописывает в твои функции плагин компилятора

Аннотация @Composable — не маркер для читателя, а инструкция компилятору. Он переписывает функцию: добавляет скрытый параметр и оборачивает тело в служебные вызовы. Примерно так (сильно упрощенно):

// что написал ты
@Composable
fun Greeting(name: String) {
    Text(text = "Привет, $name")
}

// во что это превращается
fun Greeting(name: String, $composer: Composer, $changed: Int) {
    $composer.startRestartGroup(key = -1234567)        // открыли группу в памяти
    if ($changed and 0b1110 == 0 || !$composer.skipping) {
        Text(text = "Привет, $name", $composer, 0)
    } else {
        $composer.skipToGroupEnd()                     // параметры те же — пропускаем
    }
    $composer.endRestartGroup()?.updateScope { c, _ ->
        Greeting(name, c, $changed or 1)               // как перезапустить эту функцию позже
    }
}

Три вещи, которые из этого следуют и понадобятся дальше:

  1. У каждого куска кода есть свой адрес в памяти
    startRestartGroup(key) — ключ вычисляется компилятором из позиции вызова в исходнике. Это основа всей памяти композиции, раздел 04.
  2. Функция умеет пропустить сама себя
    Если аргументы не изменились, тело не выполняется — skipToGroupEnd. Возможность сравнить аргументы зависит от стабильности типов, раздел 09.
  3. Функция умеет перезапустить сама себя
    updateScope сохраняет способ вызвать ее заново. Это и есть «граница перезапуска» из раздела 05.
Побочный факт

@Composable-функцию нельзя вызвать из обычной именно поэтому: у вызова нет $composer, который нужно передать. Ровно как suspend-функцию нельзя вызвать вне корутины.

04 Блокнот композиции: где Compose держит память

Память композиции называется slot table — плоский массив, в который рантайм по очереди записывает все, что встретил при прогоне: открытые группы, значения remember, параметры функций, ссылки на узлы дерева.

UserScreen(user)
├─ группа UserScreen        слот 0: параметр user
│  ├─ группа Row            слот 1
│  │  ├─ группа Text        слот 2: параметр "Привет, Аня"
│  │  └─ группа Button      слот 3: параметр onClick
│  └─ remember { … }        слот 4: сохраненное значение
└─ …

Устроено это как gap buffer — массив с «дырой» в позиции курсора. Вставка и удаление в месте курсора стоят O(1), а рекомпозиция как раз идет линейно, сверху вниз. Отсюда скорость: рантайм не сравнивает деревья, он идет по массиву и проверяет, совпало ли записанное с тем, что видит сейчас.

Адрес в памяти — это место в коде, а не имя переменной

Ключевой и самый неинтуитивный факт. remember не знает, в какую переменную его положили: он находит свое значение по позиции вызова в исходнике. Это называется позиционной памятью.

@Composable
fun Demo(showFirst: Boolean) {
    if (showFirst) {
        val a = remember { Random.nextInt() }   // позиция 1
        Text(text = "$a")
    } else {
        val b = remember { Random.nextInt() }   // позиция 2 — другая ячейка, другое значение
        Text(text = "$b")
    }
}

Пока структура вызовов стабильна, все работает само. Ломается там, где структура меняется динамически — в списках:

Column {
    for (item in items) {          // позиция вызова одна и та же для всех элементов
        ItemRow(item = item)       // отличаются только порядковым номером
    }
}

Удалили первый элемент — все остальные сдвинулись на позицию вверх. Для рантайма это не «удалили первый», а «у всех изменились данные»: он переиспользует ячейку первого элемента для второго вместе со всем, что там запомнено, — раскрытым состоянием, анимацией, позицией скролла вложенного списка. Отсюда key:

LazyColumn {
    items(items = items, key = { it.id }) { item ->   // адрес = id, а не порядковый номер
        ItemRow(item = item)
    }
}

// для обычных контейнеров — то же самое явным вызовом
Column {
    items.forEach { item ->
        key(item.id) { ItemRow(item = item) }
    }
}

key(…) подменяет адрес группы: вместо позиции в коде используется переданное значение. Элемент увозит свою память с собой при любой перестановке — кейс 8.

05 Границы перезапуска: почему обновляется больше, чем ждешь

Compose перезапускает не строку, где читается состояние, а ближайшую перезапускаемую функцию, внутри которой это чтение произошло — тот самый updateScope из раздела 03.

@Composable
fun ProfileScreen(viewModel: ProfileViewModel) {
    var query by remember { mutableStateOf("") }

    Column {
        Header()                                  // ← перезапускается на каждый символ
        HeavyChart(data = viewModel.chartData)    // ← и это тоже
        TextField(value = query, onValueChange = { query = it })
        Text(text = "Ищем: $query")
    }
}

Чтение query произошло в теле ProfileScreen, значит граница перезапуска — вся эта функция. Header и HeavyChart получат шанс пропустить себя по неизменившимся параметрам, но сама функция выполнится целиком на каждый введенный символ. Если параметры нестабильны — пропуска не будет и там.

Три приема сузить границу

Прием 1 — вынести читающий кусок в свою функцию

@Composable
fun ProfileScreen(viewModel: ProfileViewModel) {
    Column {
        Header()
        HeavyChart(data = viewModel.chartData)
        SearchSection()                    // чтение состояния переехало внутрь
    }
}

@Composable
private fun SearchSection() {
    var query by remember { mutableStateOf("") }
    TextField(value = query, onValueChange = { query = it })
    Text(text = "Ищем: $query")
}

Прием 2 — отложить чтение, передав лямбду вместо значения

// было: значение читается здесь, перезапускается родитель
Badge(count = state.unreadCount)

// стало: значение прочитается внутри Badge, перезапустится только он
Badge(count = { state.unreadCount })

Прием 3 — читать в лямбде модификатора, а не в теле

// было: рекомпозиция на каждый кадр анимации
Box(modifier = Modifier.offset(x = offsetX.dp))

// стало: чтение в фазе layout, композиция не перезапускается вообще
Box(modifier = Modifier.offset { IntOffset(x = offsetX.roundToPx(), y = 0) })

Третий прием — не микрооптимизация, а переход в другую фазу кадра. Об этом следующий раздел.

Изменение состояния запускает не весь конвейер, а фазу, в которой это состояние было прочитано. Прочитал в теле функции — перезапустится композиция и все, что ниже. Прочитал в лямбде offset { } — только layout и draw. Прочитал в drawBehind { } — только draw.

Правило для анимаций: чем позже фаза, тем дешевле. Перемещение, прозрачность, поворот, масштаб — все это делается на уровне layout и draw и не должно доходить до композиции. Отсюда чеклист: увидел рекомпозицию на каждый кадр анимации — ищи чтение состояния в теле функции.

07 Виды remember: разбор по одному

Сам remember устроен просто: при первом прогоне выполняет лямбду и кладет результат в слот, на следующих — достает из слота, если ключи совпали.

@Composable
inline fun <T> remember(key1: Any?, calculation: () -> T): T =
    currentComposer.cache(currentComposer.changed(key1)) { calculation() }

1. remember { } — без ключей

Значение вычисляется один раз при входе в композицию. Берется, когда результат ни от чего не зависит: держатель состояния, форматтер, компаратор, кисть.

val brush = remember {
    ShaderBrush(BitmapShader(bitmap, TileMode.REPEAT, TileMode.REPEAT))
}

Частая ошибка — вычисления вообще нет под remember

@Composable
fun ContactList(contacts: List<Contact>, comparator: Comparator<Contact>) {
    LazyColumn {
        items(contacts.sortedWith(comparator)) { … }   // сортировка на каждом прогоне
    }
}

Симптом: экран визуально корректен, но подтормаживает при любой анимации — сортировка выполняется столько раз, сколько было кадров. Лечится remember(contacts, comparator) { contacts.sortedWith(comparator) } — кейс 3.

2. remember(key1, key2) { } — с ключами

Ключи — все, от чего зависит результат. Сравниваются структурно, через ==. Ключ изменился — лямбда выполняется заново.

val avatar = remember(userId) { avatarLoader.brushFor(userId) }
// ошибка 1: ключа нет — значение устарело
val user = remember { repository.find(userId) }        // userId сменился, данные прежние

// ошибка 2: ключ нестабилен — пересчет на каждом прогоне
val filtered = remember(onClick) { items.filter(…) }   // лямбда каждый раз новая
КлючЧто происходит
лямбдаНовый объект на каждом прогоне, если компилятор ее не мемоизировал — пересчет всегда. Вместо ключа берется rememberUpdatedState
class без equalsСравнение по ссылке: новый экземпляр из ViewModel дает пересчет даже при тех же данных. Лечится data class или ключом по id
ListСравнение структурное, равный по содержимому список пересчета не даст. Опасность обратная: MutableList, измененный на месте, ключ не изменит — значение устареет
Unit, trueТо же, что вовсе без ключей. Компилятор подсвечивает проверкой OpaqueUnitKey

3. mutableStateOf и его примитивные версии

Для Int, Long, Float, Double есть отдельные фабрики: они хранят значение примитивом и не заворачивают его в объект на каждую запись.

var count by remember { mutableIntStateOf(0) }        // без упаковки в Integer

val state = remember { mutableIntStateOf(0) }
state.intValue += 1                                   // не state.value
var count by remember { mutableStateOf(0) }   // AutoboxingStateCreation
val v = state.value                           // AutoboxingStateValueProperty
var text by mutableStateOf("")                // UnrememberedMutableState — уровень Error

Симптом первых двух — «пила» по java.lang.Integer в Memory Profiler во время скролла, в тяжелых случаях пропущенные кадры из-за сборок мусора (кейс 9). Симптом третьей — поле ввода не печатает, чекбокс отщелкивает назад (кейс 1).

4. Коллекции в состоянии

Два рабочих варианта, выбор по тому, кто владеет коллекцией. Правит сам UI точечно (чек-листы, выбор, редактируемая форма) — snapshot-коллекция. Данные приходят готовым снимком из ViewModel — неизменяемый список внутри MutableState.

// вариант 1: наблюдаются сами мутации коллекции
val selected = remember { mutableStateListOf<Long>() }
selected += id

// вариант 2: наблюдается замена ссылки
var items by remember { mutableStateOf(emptyList<Item>()) }
items = items + newItem
// ошибка 1: обычная коллекция — изменения не наблюдаются вообще
val items = remember { mutableListOf<Item>() }
items.add(newItem)

// ошибка 2: изменяемая коллекция внутри состояния — MutableCollectionMutableState
val items = remember { mutableStateOf(mutableListOf("A")) }
items.value.add("B")

Симптом: «данные есть в дебаггере, но не на экране». Элемент появляется скачком позже — при первой рекомпозиции по другой причине: повороте, скролле, любом другом изменении. Кейс 5.

5. derivedStateOf — состояние, вычисленное из состояния

Нужен ровно в одном случае: вход меняется чаще, чем должен меняться выход. Позиция скролла меняется каждый кадр, а флаг «показать кнопку наверх» — дважды за весь скролл.

val listState = rememberLazyListState()
val showButton by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}
// ошибка 1: вход и выход меняются одинаково часто — лишняя обертка
val fullName by remember { derivedStateOf { "$firstName $lastName" } }
val fullName = "$firstName $lastName"                       // так правильно

// ошибка 2: без remember — объект пересоздается каждый прогон, кеш теряется
val showButton by derivedStateOf { listState.firstVisibleItemIndex > 0 }

// ошибка 3: внутри читается обычный параметр, а не состояние
val filtered by remember { derivedStateOf { items.filter { query in it.name } } }
val filtered by remember(query) { derivedStateOf { … } }    // так правильно

Третья ошибка коварнее прочих: derivedStateOf следит только за чтениями наблюдаемого состояния. Обычный параметр query в слежку не попадает, и список «залипает» на первом значении.

6. rememberSaveable — пережить поворот и смерть процесса

remember живет столько же, сколько композиция: поворот экрана его обнуляет. rememberSaveable дополнительно сохраняет значение в Bundle.

var text by rememberSaveable { mutableStateOf("") }        // переживет поворот и смерть процесса

Автоматически сохраняется все, что кладется в Bundle: примитивы, строки, Parcelable. Свой тип — через Saver:

data class Filters(val query: String, val onlyActive: Boolean)

val FiltersSaver = listSaver<Filters, Any>(
    save = { listOf(it.query, it.onlyActive) },
    restore = { Filters(query = it[0] as String, onlyActive = it[1] as Boolean) }
)

var filters by rememberSaveable(stateSaver = ...) { mutableStateOf(Filters("", false)) }
Ограничение Bundle

Bundle — не хранилище данных, а транспорт для восстановления экрана. Лимит на всю транзакцию — около 1 МБ на процесс, практический потолок для одного экрана — десятки килобайт. Список из сети туда не кладут: он живет во ViewModel и грузится заново, а в rememberSaveable остается позиция скролла и введенный текст.

08 Где состояние обязано жить

Решение принимается до написания кода и начинается с одного различения.

ПризнакСостояние UI-элементаСостояние экрана
Что описываетсвойство самого элемента: раскрыт, проскроллен, анимируется что показать: данные приложения
Откуда беретсяиз самого UIиз слоя данных: репозиторий, база, сеть
Поворот экранатеряет смысл вместе с UIданные не становятся невалидными
Где живетremember, rememberSaveable, держатель ViewModel

Тест из двух вопросов. Может ли значение приехать из репозитория или уйти в него? Тогда это состояние экрана. Теряет ли оно смысл после пересоздания экрана? Тогда это состояние UI-элемента.

Правило подъема состояния

Состояние поднимается до самого низкого общего предка всех, кто его читает и пишет. Владелец отдает вниз неизменяемое значение и события для его изменения.

@Composable
private fun ConversationScreen(messages: List<Message>) {
    val scope = rememberCoroutineScope()
    val listState = rememberLazyListState()        // нужен и списку, и полю ввода

    MessagesList(messages = messages, listState = listState)
    UserInput(onMessageSent = { scope.launch { listState.scrollToItem(0) } })
}

@Composable
private fun MessagesList(
    messages: List<Message>,
    listState: LazyListState = rememberLazyListState()   // дефолт: никому не нужен — остается внутри
) {
    LazyColumn(state = listState) { … }
}

Ошибка в одну сторону — поднять выше необходимого: состояние лежит в корне экрана, читают его два листа, и перезапускается вся ветка вместо двух узлов (кейс 6, кейс 10). Ошибка в другую — оставить внизу то, что нужно соседям, и потом синхронизировать руками.

Обычный класс — держатель состояния

Признак: логика отображения стала сложной (несколько полей, несколько операций), а компонент переиспользуемый — панель поиска, группа чипов, календарь. Бизнес-логики нет, данные приложения не нужны.

@Stable
class SearchBarState(
    private val suggestions: StateFlow<List<Suggestion>>,
    private val onSubmit: (String) -> Unit,
    val focusRequester: FocusRequester
) {
    var query by mutableStateOf("")
        private set

    val isClearVisible: Boolean get() = query.isNotEmpty()

    fun onQueryChange(value: String) { query = value }
}

@Composable
fun rememberSearchBarState(
    suggestions: StateFlow<List<Suggestion>>,
    onSubmit: (String) -> Unit,
    focusRequester: FocusRequester = remember { FocusRequester() }
): SearchBarState = remember(suggestions, onSubmit, focusRequester) {
    SearchBarState(suggestions, onSubmit, focusRequester)
}

Почему тут нельзя ViewModel — три независимые причины:

  1. Скоуп один на экран
    ViewModel привязана к экрану, а не к месту вызова. Две группы чипов на одном экране получат одну и ту же ViewModel и слипнутся в одно состояние — кейс 11.
  2. Живет дольше, чем нужно
    ViewModel переживает поворот, а состояние UI-элемента обязано пересоздаться вместе с UI.
  3. Нет доступа к тому, что нужно UI
    ViewModel не имеет права держать Context и Resources, а логике отображения они нужны.

ViewModel — когда без нее нельзя

Достаточно любого признака: нужна бизнес-логика или данные из репозитория; suspend-операция не должна прерваться при повороте; состояние живет, пока экран в стеке навигации; состояние делят большие части UI.

@HiltViewModel
class ConversationViewModel @Inject constructor(
    savedStateHandle: SavedStateHandle,
    messagesRepository: MessagesRepository
) : ViewModel() {

    private val channelId: String = savedStateHandle["channelId"] ?: error("no channelId")

    val messages: StateFlow<List<Message>> = messagesRepository
        .getLatestMessages(channelId = channelId)
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = emptyList()
        )
}
ViewModel не передается вниз по дереву

Ее принимает только экранная composable, и то с дефолтом hiltViewModel(). Дальше вниз идут значения и лямбды. Иначе дочерний компонент нельзя ни переиспользовать, ни показать в превью, ни протестировать отдельно.

Где хранить значение?
│
├─ приезжает из репозитория или уходит в него       → ViewModel
│    └─ и должно пережить смерть процесса           → SavedStateHandle
│
├─ теряет смысл при пересоздании экрана
│    ├─ пользователь не должен его потерять         → rememberSaveable
│    └─ можно потерять                              → remember
│
└─ логика отображения сложная, компонент общий      → класс-держатель + rememberXxxState()

09 Стабильность и strong skipping

Пропуск функции возможен, только если Compose может сравнить аргументы с прошлыми. Тип, про который он способен это сказать, называют стабильным: он либо неизменяемый, либо сам сообщает об изменениях.

СтабильноНестабильно
Int, String, enum, лямбда, data class из val стабильных полей, MutableState, ImmutableList List / Map / Set (интерфейсы), класс с var, тип из модуля, собранного без плагина Compose

С Kotlin 2.0.20 по умолчанию включен strong skipping. Он меняет две вещи: пропускаться могут все перезапускаемые функции, даже с нестабильными параметрами (такие параметры сравниваются по ссылке, а не по содержимому), и лямбды с нестабильными захватами компилятор мемоизирует сам.

Что это не отменяет

Сравнение по ссылке не спасает, когда объект новый, а содержимое то же: state.copy(items = items) — другая ссылка, значит прогон будет. Поэтому @Immutable, @Stable и неизменяемые коллекции (kotlinx.collections.immutable) остаются рабочим инструментом — кейс 12.

Часть II

Двенадцать кейсов

Схема в каждом одна: задача, код как его пишут, что видит пользователь, объяснение через разделы части I и правильный вариант.

Кейс 1. Чекбокс «Согласен с условиями» отщелкивает назад

Экран оформления заказа, обязательная галочка перед оплатой.

Как пишут
@Composable
fun AgreementRow(modifier: Modifier = Modifier) {
    var isChecked by mutableStateOf(false)          // забыли remember

    Row(modifier = modifier, verticalAlignment = Alignment.CenterVertically) {
        Checkbox(checked = isChecked, onCheckedChange = { isChecked = it })
        Text(text = "Согласен с условиями")
    }
}
Что видит пользователь
  • Нажал на чекбокс
  • Галочка мигнула и вернулась в пустое состояние
  • Кнопка «Оплатить» так и остается неактивной, оформить заказ невозможно
Почему

mutableStateOf дает наблюдение, но не память (раздел 02). Клик изменил значение, изменение запустило рекомпозицию, а рекомпозиция выполнила строку заново и создала новое состояние с false. Бесконечный цикл «изменил — потерял».

Как надо
var isChecked by remember { mutableStateOf(false) }

А если галочка должна пережить поворот экрана — rememberSaveable. И еще честнее: согласие с условиями обычно относится к состоянию формы, а не элемента, и живет во ViewModel вместе с остальными полями.

ПравилоLint ловит это проверкой UnrememberedMutableState с уровнем Error — не отключать и не игнорировать.

Кейс 2. Введенный текст исчезает при повороте

Форма отзыва о заказе: поле комментария на несколько строк.

Как пишут
@Composable
fun ReviewForm(onSubmit: (String) -> Unit) {
    var comment by remember { mutableStateOf("") }

    Column {
        OutlinedTextField(
            value = comment,
            onValueChange = { comment = it },
            label = { Text(text = "Ваш отзыв") }
        )
        Button(onClick = { onSubmit(comment) }) { Text(text = "Отправить") }
    }
}
Что видит пользователь
  • Написал развернутый отзыв на десять строк
  • Повернул телефон, чтобы было удобнее печатать
  • Поле пустое, текст потерян целиком
  • То же самое, если свернуть приложение и вернуться через час — процесс убит
Почему

remember живет ровно столько же, сколько композиция. Поворот экрана пересоздает Activity, композиция строится заново, слоты пусты (раздел 07, таблица «что переживает что»).

Как надо
var comment by rememberSaveable { mutableStateOf("") }

Работает, потому что String кладется в Bundle сам. Для своего типа нужен Saver, а для больших данных — ViewModel с SavedStateHandle (кейс 10).

ПравилоВсе, что ввел пользователь руками, — минимум rememberSaveable.

Кейс 3. Список подтормаживает на анимации

Список контактов с сортировкой и фильтром по строке поиска.

Как пишут
@Composable
fun ContactList(
    contacts: List<Contact>,
    query: String,
    comparator: Comparator<Contact>
) {
    val visible = contacts
        .filter { it.name.contains(query, ignoreCase = true) }
        .sortedWith(comparator)                      // на каждом прогоне заново

    LazyColumn {
        items(items = visible, key = { it.id }) { contact ->
            ContactRow(contact = contact)
        }
    }
}
Что видит пользователь
  • Список работает правильно, данные верные
  • Любая анимация рядом идет рывками
  • На тысяче контактов скролл ощутимо дергается, телефон греется
Почему

Тело функции выполняется на каждую рекомпозицию — а их столько же, сколько кадров у любой соседней анимации. Фильтрация и сортировка тысячи элементов выполняются 60 раз в секунду и каждый раз аллоцируют новый список.

Как надо
val visible = remember(contacts, query, comparator) {
    contacts
        .filter { it.name.contains(query, ignoreCase = true) }
        .sortedWith(comparator)
}

Ключи — ровно те три значения, от которых зависит результат. Изменился любой — пересчет, не изменился ни один — берется готовое из слота.

ПравилоЛюбое вычисление в теле composable, дороже сложения, — под remember с полным набором ключей.

Кейс 4. На экране данные предыдущего пользователя

Карточка профиля, открывается из списка сотрудников компании.

Как пишут
@Composable
fun ProfileCard(userId: Long, repository: UserRepository) {
    val user = remember { repository.findCached(userId) }     // ключа нет

    Column {
        Text(text = user.name, style = MaterialTheme.typography.titleLarge)
        Text(text = user.position)
    }
}
Что видит пользователь
  • Открыл карточку Ани — все верно
  • Свайпнул на следующего сотрудника
  • В шапке имя Бориса, а должность и телефон остались Анины
Почему

Без ключей remember возвращает значение из слота на всех прогонах после первого (раздел 07). Смена userId — это рекомпозиция той же группы, значит слот тот же, значит и значение то же.

Как надо
val user = remember(userId) { repository.findCached(userId) }
ПравилоВсе, что участвует в вычислении, обязано стоять в ключах. Симптом пропущенного ключа — данные предыдущего элемента без единой ошибки в логах.

Кейс 5. Добавил товар в список — на экране ничего

Экран создания заказа: товары добавляются по одному кнопкой.

Как пишут
@Composable
fun OrderBuilder(catalog: List<Product>) {
    val chosen = remember { mutableListOf<Product>() }      // обычный список

    Column {
        Button(onClick = { chosen.add(catalog.first()) }) {
            Text(text = "Добавить товар")
        }
        chosen.forEach { product ->
            Text(text = product.name)
        }
    }
}
Что видит пользователь
  • Нажал «Добавить товар» пять раз
  • Список на экране пуст, хотя в дебаггере в нем пять элементов
  • Повернул экран или проскроллил — товары появились скачком, все сразу
Почему

mutableListOf — обычная коллекция, ее изменения не являются изменением состояния. Compose ничего не заметил, рекомпозиции нет. При следующей рекомпозиции по другой причине тело выполнилось и отрисовало актуальное содержимое — отсюда «появились скачком».

Как надо
val chosen = remember { mutableStateListOf<Product>() }   // snapshot-коллекция
chosen += catalog.first()

Или второй вариант — неизменяемый список внутри состояния, с заменой ссылки:

var chosen by remember { mutableStateOf(emptyList<Product>()) }
chosen = chosen + catalog.first()

Что нельзя ни в каком виде — изменяемая коллекция внутри состояния (mutableStateOf(mutableListOf())): ссылка не меняется, мутации не наблюдаются, Lint ругается проверкой MutableCollectionMutableState.

ПравилоСимптом «в дебаггере есть, на экране нет» — всегда про ненаблюдаемую коллекцию.

Кейс 6. Весь экран перерисовывается на каждый введенный символ

Экран компании: шапка с логотипом, график статистики и поиск по услугам.

Как пишут
@Composable
fun CompanyScreen(viewModel: CompanyViewModel = hiltViewModel()) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    var query by remember { mutableStateOf("") }

    Column {
        CompanyHeader(company = state.company)          // перезапускается на каждый символ
        StatisticsChart(points = state.points)          // и это тоже

        OutlinedTextField(value = query, onValueChange = { query = it })
        ServicesList(services = state.services.filter { it.name.contains(query) })
    }
}
Что видит пользователь
  • Начал набирать название услуги
  • Ввод отстает от печати, буквы появляются рывками
  • График подмигивает при каждом символе
  • В Layout Inspector счетчик рекомпозиций у графика растет вместе с вводом
Почему

Граница перезапуска — ближайшая перезапускаемая функция, внутри которой прочиталось состояние (раздел 05). query читается в теле CompanyScreen, значит перезапускается весь экран. Дочерние функции могли бы пропустить себя, но List<Point> нестабилен, и пропуска не будет (раздел 09).

Как надо
@Composable
fun CompanyScreen(viewModel: CompanyViewModel = hiltViewModel()) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    Column {
        CompanyHeader(company = state.company)
        StatisticsChart(points = state.points)
        ServicesSection(services = state.services)     // состояние уехало внутрь
    }
}

@Composable
private fun ServicesSection(services: List<Service>) {
    var query by remember { mutableStateOf("") }
    val visible = remember(services, query) {
        services.filter { it.name.contains(query, ignoreCase = true) }
    }

    OutlinedTextField(value = query, onValueChange = { query = it })
    ServicesList(services = visible)
}
ПравилоСостояние читается как можно ниже по дереву. Своя функция вокруг читающего куска — самый дешевый способ сузить границу перезапуска.

Кейс 7. Кнопка «наверх» стоит дорого

Длинный список операций, кнопка возврата к началу появляется после первого экрана прокрутки.

Как пишут
@Composable
fun OperationsList(items: List<Operation>) {
    val listState = rememberLazyListState()
    val showButton = listState.firstVisibleItemIndex > 0     // чтение в теле функции

    Box {
        LazyColumn(state = listState) {
            items(items = items, key = { it.id }) { OperationRow(operation = it) }
        }
        if (showButton) ScrollToTopButton(listState = listState)
    }
}
Что видит пользователь
  • Кнопка появляется и исчезает правильно
  • Прокрутка не гладкая, особенно на бюджетных устройствах
  • В Layout Inspector OperationsList рекомпозируется десятки раз в секунду, пока палец на экране
Почему

firstVisibleItemIndex меняется на каждый сдвиг строки. Чтение в теле функции подписывает всю функцию на эти изменения (раздел 05), хотя результат — булев флаг, который за весь скролл меняется два раза.

Как надо
val showButton by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}

derivedStateOf пересчитывает выражение при каждом изменении входа, но уведомляет читателей только когда результат стал другим. Рекомпозиций — две за весь скролл вместо сотен.

Когда derivedStateOf не нужен

Если вход меняется не чаще выхода — это чистые накладные расходы. "$firstName $lastName" в обертке не нуждается: имя меняется ровно тогда, когда меняется строка.

ПравилоВход меняется чаще, чем должен меняться выход, — derivedStateOf. В остальных случаях — обычное выражение.

Кейс 8. Удалил один пункт — развернулся другой

Список сохраненных адресов, каждый раскрывается по тапу и удаляется свайпом.

Как пишут
@Composable
fun AddressList(addresses: List<Address>, onDelete: (Long) -> Unit) {
    LazyColumn {
        items(addresses) { address ->                 // key не задан
            AddressRow(address = address, onDelete = { onDelete(address.id) })
        }
    }
}

@Composable
private fun AddressRow(address: Address, onDelete: () -> Unit) {
    var isExpanded by remember { mutableStateOf(false) }   // состояние живет в элементе
    ...
}
Что видит пользователь
  • Раскрыл третий адрес, чтобы посмотреть детали
  • Удалил первый адрес свайпом
  • Раскрытым оказался четвертый — состояние съехало вместе со сдвигом
  • Анимация удаления проигрывается не на том элементе
Почему

Без key адрес группы в памяти композиции — порядковый номер (раздел 04). После удаления первого элемента все сдвинулись, и рантайм переиспользовал слоты: элемент, который был третьим, получил память бывшего второго вместе с его isExpanded.

Как надо
items(items = addresses, key = { it.id }) { address ->
    AddressRow(address = address, onDelete = { onDelete(address.id) })
}

Теперь адрес группы — идентификатор самого элемента, и память переезжает вместе с ним. В обычном Column то же самое делается явным key(item.id) { … }.

Правилоkey в списках обязателен всегда, когда элементы могут добавляться, удаляться или переставляться. Ключ — стабильный идентификатор данных, не индекс.

Кейс 9. «Пила» в профайлере во время анимации

Анимированный счетчик бонусов на главном экране.

Как пишут
var points by remember { mutableStateOf(0) }        // объектная версия для Int

LaunchedEffect(target) {
    animate(initialValue = 0f, targetValue = target.toFloat()) { value, _ ->
        points = value.toInt()                     // ~60 записей в секунду
    }
}
Что видит пользователь
  • Анимация идет, число растет — визуально все хорошо
  • В Memory Profiler «пила» по java.lang.Integer
  • На слабых устройствах анимация дергается из-за сборок мусора
Почему

mutableStateOf(0) хранит Int как объект: каждая запись создает новый Integer. Шестьдесят аллокаций в секунду на каждое такое состояние.

Как надо
var points by remember { mutableIntStateOf(0) }     // значение хранится примитивом

Для Long, Float, Double есть такие же фабрики. При работе без делегата читать нужно через intValue, а не value — иначе упаковка вернется.

ПравилоПримитив в состоянии — примитивной фабрикой. Lint подсказывает проверками AutoboxingStateCreation и AutoboxingStateValueProperty.

Кейс 10. Заполненная форма пропала после звонка

Длинная форма записи на услугу: дата, мастер, комментарий, промокод.

Как пишут
@HiltViewModel
class BookingViewModel @Inject constructor(...) : ViewModel() {

    private val _form = MutableStateFlow(BookingForm())      // только в памяти процесса
    val form: StateFlow<BookingForm> = _form.asStateFlow()

    fun onCommentChange(value: String) {
        _form.update { it.copy(comment = value) }
    }
}
Что видит пользователь
  • Заполнил форму наполовину
  • Свернул приложение, чтобы посмотреть время в календаре, там задержался
  • Вернулся — форма пустая: система убила процесс ради памяти
  • Поворот экрана при этом работал нормально, поэтому баг не находят в тестах
Почему

ViewModel переживает поворот, но не смерть процесса (раздел 07, таблица). Разница видна только на реальном сценарии со свернутым приложением — воспроизводится опцией «Не сохранять действия» в настройках разработчика.

Как надо
@HiltViewModel
class BookingViewModel @Inject constructor(
    private val savedStateHandle: SavedStateHandle
) : ViewModel() {

    val comment: StateFlow<String> = savedStateHandle.getStateFlow(key = COMMENT, initialValue = "")

    fun onCommentChange(value: String) {
        savedStateHandle[COMMENT] = value        // переживет смерть процесса
    }

    private companion object {
        const val COMMENT = "comment"
    }
}

В SavedStateHandle кладется только то, что нельзя получить заново: введенный текст, выбранная дата, шаг мастера. Список мастеров туда не кладут — он грузится с сервера повторно.

ПравилоПоворот — это ViewModel. Смерть процесса — SavedStateHandle или rememberSaveable. Проверяется опцией «Не сохранять действия», а не поворотом.

Кейс 11. Две группы фильтров ведут себя как одна

Экран поиска: сверху чипы категорий, снизу чипы городов. Компонент один и тот же, переиспользуемый.

Как пишут
@Composable
fun ChipsGroup(items: List<String>, viewModel: ChipsViewModel = hiltViewModel()) {
    val selected by viewModel.selected.collectAsStateWithLifecycle()
    ...
}

// на экране
Column {
    ChipsGroup(items = categories)
    ChipsGroup(items = cities)
}
Что видит пользователь
  • Выбрал категорию «Красота»
  • В группе городов подсветился чип на той же позиции
  • Сброс фильтра в одной группе сбрасывает обе
Почему

hiltViewModel() отдает ViewModel, привязанную к владельцу — экрану или destination, а не к месту вызова. Оба компонента получили один и тот же экземпляр и делят состояние (раздел 08).

Как надо
@Stable
class ChipsGroupState(initial: Set<String> = emptySet()) {
    var selected by mutableStateOf(initial)
        private set

    fun toggle(item: String) {
        selected = if (item in selected) selected - item else selected + item
    }
}

@Composable
fun rememberChipsGroupState(): ChipsGroupState = remember { ChipsGroupState() }

@Composable
fun ChipsGroup(
    items: List<String>,
    state: ChipsGroupState = rememberChipsGroupState()   // свое состояние у каждого вызова
) { … }

Если выбор нужен экрану целиком — состояние поднимается наверх и передается параметром, но по-прежнему не через ViewModel внутри компонента.

ПравилоViewModel — на экран, не на компонент. Переиспользуемому компоненту нужен класс-держатель и своя rememberXxxState().

Кейс 12. Экран не пропускает рекомпозиции, хотя данные не менялись

Экран заказа с несколькими секциями: товары, доставка, оплата.

Как пишут
data class OrderUiState(
    val items: List<OrderItem>,          // интерфейс List — нестабильный тип
    val delivery: Delivery,
    val isPaying: Boolean
)

@Composable
fun OrderScreen(state: OrderUiState) {
    Column {
        ItemsSection(items = state.items)          // не пропускается
        DeliverySection(delivery = state.delivery)
        PayButton(isPaying = state.isPaying)
    }
}
Что видит пользователь
  • Нажал «Оплатить», пошел индикатор
  • Секция товаров и блок доставки перерисовываются вместе с ним
  • На длинном заказе кнопка отзывается с задержкой
Почему

List — интерфейс, за ним может стоять изменяемая реализация, поэтому Compose считает тип нестабильным (раздел 09). Strong skipping это частично лечит — параметр сравнивается по ссылке, — но state.copy(isPaying = true) создает новый объект состояния, и хотя items тот же самый список по ссылке, разбор идет по каждому параметру заново.

Как надо
@Immutable
data class OrderUiState(
    val items: ImmutableList<OrderItem>,   // kotlinx.collections.immutable
    val delivery: Delivery,
    val isPaying: Boolean
)

Второй прием — не тащить весь state вниз, а передавать секциям ровно то, что им нужно: тогда смена isPaying вообще не касается параметров других секций.

Сначала измерить

Стабильность — последняя оптимизация, а не первая. Порядок: счетчики рекомпозиций в Layout Inspector → отчет compose compiler о стабильности → правки. Выводы делаются по release-сборке, debug врет из-за отключенных оптимизаций.

ПравилоНестабильный параметр — это не «плохой код», а причина, по которой функция не может пропустить сама себя. Значение имеет только там, где рекомпозиции реально мешают.

Чеклист, когда экран тормозит

  1. Проверить, нужна ли композиция вообще: не решается ли задача чтением состояния в лямбде модификатора — offset { }, graphicsLayer { }, drawBehind { }.
  2. Найти, где состояние читается, и опустить чтение ниже: своя функция вокруг читающего куска или лямбда вместо значения.
  3. Если источник меняется чаще результата — завернуть в derivedStateOf под remember.
  4. Проверить параметры дочерних функций: объекты, собираемые в теле родителя, — под remember с ключами.
  5. Проверить, что у элементов списков есть key.
  6. Примитивы в состоянии — примитивными фабриками.
  7. Замерить, а не угадать: счетчики рекомпозиций в Layout Inspector и отчет компилятора о стабильности. Выводы — по release-сборке.
Все в трех фразах

Compose прогоняет твои функции и ведет блокнот: какая группа кода что запомнила. remember — ячейка этого блокнота, найденная по месту вызова в коде. Рекомпозиция — повторный прогон помеченных групп, и вся оптимизация сводится к двум вопросам: насколько узок кусок, который прогоняется заново, и что в нем создается заново без нужды.
