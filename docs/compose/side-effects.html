Механика: как это устроено

01 Что такое сайд-эффект и почему тело функции для него не годится

Сайд-эффект — любое изменение, которое переживает прогон composable и видно снаружи него: запрос в сеть, запись в базу, событие аналитики, показ снекбара, регистрация слушателя, переход на другой экран.

Начнем с экрана, написанного так, как его написал бы человек с опытом в XML. Логика привычная: пришли на экран — загрузились, отправили аналитику, подписались на события.

OrderDetailsScreen.kt — так делать нельзя

@Composable
fun OrderDetailsScreen(
    orderId: Long,
    viewModel: OrderViewModel,
    onBack: () -> Unit
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    viewModel.loadOrder(orderId)                                  // 1
    analytics.logScreen(screen = "order", orderId = orderId)      // 2
    orderEvents.addListener { viewModel.onOrderChanged() }        // 3

    Scaffold(
        topBar = { OrderTopBar(title = state.title, onBack = onBack) }
    ) { padding ->
        OrderContent(state = state, modifier = Modifier.padding(padding))
    }
}

Три строки, три разных бага. Чтобы понять, откуда они берутся, нужно принять одну вещь про тело composable: оно описывает картинку и может быть выполнено сколько угодно раз. У прогона четыре свойства, и каждое по отдельности ломает императивный код.

  1. Прогон повторяется непредсказуемо часто
    Рекомпозиция запускается от любого прочитанного состояния. Здесь state читается в теле, значит каждый ответ сервера, каждое изменение статуса заказа, каждый спиннер — это новый прогон всех трех строк.
  2. Прогон может быть отменен на середине
    Рантайм вправе бросить незаконченную композицию, если данные снова изменились. Запрос, который уже ушел из строки 1, отменять некому.
  3. Порядок и поток не гарантированы
    Compose не обещает ни порядок выполнения соседних composable, ни поток, на котором они выполнятся. Рассуждение «сначала загрузится, потом отрисуется» опоры не имеет.
  4. Прогон может не дойти до экрана
    Отброшенная композиция ничего не применяет. Аналитика показа уже ушла, а экран пользователь так и не увидел.

Отсюда правило, которое дальше будет повторяться в каждом кейсе: в теле composable нет глаголов. Тело описывает: какие элементы показать и с какими данными. Все, что делает, живет в эффектах.

OrderDetailsScreen.kt — так правильно

@Composable
fun OrderDetailsScreen(
    orderId: Long,
    viewModel: OrderViewModel,
    onBack: () -> Unit
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    LaunchedEffect(orderId) {                       // 1: работа, привязанная к экрану
        viewModel.loadOrder(orderId)
    }

    LaunchedEffect(orderId) {                       // 2: однократное событие
        analytics.logScreen(screen = "order", orderId = orderId)
    }

    DisposableEffect(orderId) {                     // 3: подписка со снятием
        val listener = OrderListener { viewModel.onOrderChanged() }
        orderEvents.addListener(listener)
        onDispose { orderEvents.removeListener(listener) }
    }

    Scaffold(
        topBar = { OrderTopBar(title = state.title, onBack = onBack) }
    ) { padding ->
        OrderContent(state = state, modifier = Modifier.padding(padding))
    }
}

Три инструмента, три разных признака задачи. Почему именно так — в разделе 06; сначала нужно понять, что вообще происходит с composable во времени.

02 Жизнь composable: три момента, и все

вход в композицию          функция выполнилась впервые, ее группа появилась
     │                     в памяти композиции
     ├── рекомпозиция      параметры или состояние изменились, функция
     ├── рекомпозиция      выполнилась заново; группа та же самая
     ├── ...
     │
уход из композиции         группы больше нет: ветка if стала ложной, элемент
                           уехал из списка, экран сняли с навигации

У composable нет onCreate, onStart, onDestroy. Есть только эти три момента, и эффекты — единственный способ повесить на них код. Посмотрим, как это выглядит в реальной разметке.

Вход и уход происходят чаще, чем кажется

@Composable
fun WalletScreen(state: WalletUiState) {
    Column {
        if (state.hasPromo) {
            PromoBanner(promo = state.promo)      // вход при hasPromo = true,
        }                                         // уход при hasPromo = false

        LazyColumn {
            items(state.cards, key = { it.id }) { card ->
                CardRow(card = card)              // вход, когда элемент подъезжает к экрану,
            }                                     // уход, когда уезжает за его пределы
        }
    }
}

Каждый эффект внутри PromoBanner и CardRow проживет столько жизней, сколько раз баннер покажут и сколько раз строку проскроллят туда-обратно. Это причина кейса 11 и половины проблем с аналитикой в списках.

Композиция — не жизненный цикл экрана

Пользователь свернул приложение: Activity получила onStop, а композиция осталась на месте — из нее ничего не уходило. Значит LaunchedEffect продолжает работать, поток продолжает собираться, сокет остается открытым. Привязка к STARTED и RESUMED — это отдельная работа: collectAsStateWithLifecycle, LifecycleResumeEffect, repeatOnLifecycle. Кейс 9 полностью про это.

03 Из чего сделан эффект

Все инструменты из этой статьи сделаны из одного механизма. Разберемся с ним один раз — и дальше поведение любого эффекта будет выводиться, а не запоминаться.

Рантайм умеет сообщать объекту, положенному в remember, о трех событиях его жизни:

interface RememberObserver {
    fun onRemembered()   // значение попало в композицию
    fun onForgotten()    // значение выброшено: ушла группа или сменился ключ
    fun onAbandoned()    // композицию отбросили, значение так и не доехало до экрана
}

LaunchedEffect — это remember с ключами, в который положен объект-обертка над корутиной. Реализация в androidx, сокращенно:

@Composable
fun LaunchedEffect(key1: Any?, block: suspend CoroutineScope.() -> Unit) {
    val applyContext = currentComposer.applyCoroutineContext
    remember(key1) { LaunchedEffectImpl(applyContext, block) }      // вот и весь эффект
}

private class LaunchedEffectImpl(
    parentCoroutineContext: CoroutineContext,
    private val task: suspend CoroutineScope.() -> Unit
) : RememberObserver {

    private val scope = CoroutineScope(parentCoroutineContext)
    private var job: Job? = null

    override fun onRemembered() {
        job?.cancel("Old job was still running!")
        job = scope.launch(block = task)          // корутина стартует ЗДЕСЬ
    }

    override fun onForgotten() { job?.cancel(); job = null }
    override fun onAbandoned() { job?.cancel(); job = null }
}

DisposableEffect устроен так же, только вместо корутины хранит результат блока onDispose и вызывает его в onForgotten:

private class DisposableEffectImpl(
    private val effect: DisposableEffectScope.() -> DisposableEffectResult
) : RememberObserver {

    private var onDisposeResult: DisposableEffectResult? = null

    override fun onRemembered() { onDisposeResult = InternalScope.effect() }   // тело эффекта
    override fun onForgotten() { onDisposeResult?.dispose(); onDisposeResult = null }
    override fun onAbandoned() { }
}

Из этих двадцати строк следует все поведение эффектов. Таблица — то же самое, но по-русски:

Что произошлоЧто делает рантаймЧто это значит
Composable появился на экране onRemembered Корутина стартует; тело DisposableEffect выполняется
Рекомпозиция, ключи не изменились ничего Объект тот же, корутина продолжает работать с прежними значениями
Рекомпозиция, ключ изменился onForgotten старого, затем onRemembered нового Отмена и перезапуск; onDispose вызывается ДО нового захода
Composable ушел из композиции onForgotten Корутина отменена, onDispose выполнен
Композицию отбросили onAbandoned Эффект не стартовал вовсе — он и не должен был
Главный вывод части I

Ключи эффекта — это ключи remember, а не «зависимости». Рантайм сравнивает их через equals: совпали — объект тот же, эффект продолжает работать; разошлись — старый выброшен, создан новый. Любая ошибка с ключами объясняется этой одной фразой.

Исключение из ряда — SideEffect: он ничего не запоминает и не имеет ключей. Его лямбда просто записывается в список отложенной работы текущего кадра (composer.recordSideEffect) и выполняется после того, как композиция успешно применилась.

04 Когда именно эффект выполняется внутри кадра

изменилось состояние
        │
        ▼

 │   composition    │   тела эффектов НЕ выполняются — они только регистрируются

          ▼

 │                  │   выполняются SideEffect; стартуют корутины LaunchedEffect

          ▼
 ┌──────────────────┐

Проверим схему кодом. Что напечатает этот экран при первом появлении?

@Composable
fun OrderScreen(orderId: Long) {
    Timber.d("1: тело начало выполняться")

    LaunchedEffect(orderId) {
        Timber.d("3: тело эффекта")
    }

    SideEffect {
        Timber.d("4: SideEffect")
    }

    Timber.d("2: тело закончило выполняться")
    OrderContent()
}

Порядок в логе — 1, 2, 4, 3. Строки тела выполняются первыми, потому что на своей строке LaunchedEffect только регистрируется. Дальше идет фаза apply: сначала SideEffect, затем стартует корутина.

  1. Тело эффекта не выполняется на своей строке. Код ниже по телу отработает раньше. Логика «эффект посчитает, а следующая строка прочитает результат» не работает никогда.
  2. Очистка идет перед новым заходом. При смене ключа DisposableEffect сначала выполнит onDispose старого, потом тело нового — слушатель не задвоится.
  3. Корутина стартует на главном потоке (диспетчер композиции, AndroidUiDispatcher.Main). Тяжелую работу внутри нужно уводить самому: withContext(Dispatchers.IO) или репозиторием, который уже это делает.

05 Ключи: договор о перезапуске

Правило одно: в ключах ровно то, от чего зависит смысл эффекта. Дальше — четыре способа его нарушить, все четыре встречаются в кейсах части II.

Что с ключамиЧто делает рантаймКак выглядит на экранеКейс
Недостача Объект тот же, перезапуска нет Открыл другой заказ — данные прежнего 1, 12
Избыток Лишние отмены и рестарты Запрос уходит по кругу, спиннер моргает 8
Нестабильный ключ Ключ не равен себе между прогонами Экран не может успокоиться, таймер сбрасывается 4

Разберем нестабильный ключ подробно — он самый неочевидный. Что не равно самому себе на следующем прогоне:

LaunchedEffect(onFinished) { … }            // лямбда: новый объект на каждом прогоне
LaunchedEffect(viewModel.buildConfig()) { }  // результат вызова: новый объект
LaunchedEffect(items) { … }                  // список, собранный в теле родителя
LaunchedEffect(User(id, name)) { … }         // не data class — equals по ссылке
LaunchedEffect(orderId) { … }                // примитив
LaunchedEffect(user.id) { … }                // поле-примитив вместо объекта
LaunchedEffect(state.filter) { … }           // data class или enum — equals по значению
LaunchedEffect(Unit) { … }                   // осознанно один раз
Отдельная ловушка

Чтение State внутри уже запущенной корутины ничего не подписывает. Композиция наблюдает за состоянием, корутина — нет: разбудить ее изменение не может. Прочитал значение до цикла — дальше работаешь со снимком; перечитываешь на каждой итерации — значение свежее, но момент изменения все равно пропускаешь. Реакция именно на изменение — это snapshotFlow, кейс 8.

Проверка на ревью в одно движение: прочитать тело эффекта, выписать все изменяемые имена, сверить со скобками. Каждое имя обязано быть либо в скобках, либо обернуто в rememberUpdatedState. Третьего варианта нет.

06 Восемь инструментов, по одному

Каждый — с законченным примером: экран целиком, где нужно — вместе с ViewModel. Порядок от самого частого к самому редкому.

1. LaunchedEffect(keys) — работа, привязанная к присутствию на экране

Запускает корутину при входе в композицию, отменяет при уходе, перезапускает при смене ключа. Рабочая лошадь: загрузка, ожидание, таймеры, разовые события.

CertificateScreen.kt

@Composable
fun CertificateScreen(
    certificateId: Long,
    viewModel: CertificateViewModel = hiltViewModel(),
    onBack: () -> Unit
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    LaunchedEffect(certificateId) {
        viewModel.load(certificateId = certificateId)
    }

    Scaffold(topBar = { CertificateTopBar(onBack = onBack) }) { padding ->
        when (state) {
            is CertificateUiState.Loading -> FullscreenProgress(Modifier.padding(padding))
            is CertificateUiState.Error -> ErrorStub(
                error = (state as CertificateUiState.Error).message,
                onRetry = { viewModel.load(certificateId = certificateId) },
                modifier = Modifier.padding(padding)
            )
            is CertificateUiState.Content -> CertificateContent(
                certificate = (state as CertificateUiState.Content).certificate,
                modifier = Modifier.padding(padding)
            )
        }
    }
}

CertificateViewModel.kt

@HiltViewModel
class CertificateViewModel @Inject constructor(
    private val repository: CertificateRepository
) : ViewModel() {

    private val _state = MutableStateFlow<CertificateUiState>(CertificateUiState.Loading)
    val state: StateFlow<CertificateUiState> = _state.asStateFlow()

    fun load(certificateId: Long) {
        viewModelScope.launch {
            _state.value = CertificateUiState.Loading
            runCatching { repository.getCertificate(id = certificateId) }
                .onSuccess { certificate ->
                    _state.value = CertificateUiState.Content(certificate = certificate)
                }
                .onFailure { error ->
                    ensureActive()          // отмена тоже приходит сюда — пробрасываем ее дальше
                    _state.value = CertificateUiState.Error(message = error.messageOrDefault())
                }
        }
    }
}
Про ensureActive в onFailure

Отмена корутины приходит обычным исключением CancellationException, а runCatching ловит любой Throwable — значит отмена попадает в onFailure наравне с ошибкой сети. Без ensureActive() состояние отмененной загрузки доедет до экрана: пользователь переключил сертификат, старый запрос отменился и записал Error поверх Loading нового. Правило общее: runCatching вокруг suspend-вызова обязан пробрасывать отмену дальше.

берем
нужна корутина, живущая столько же, сколько composable на экране
не берем
работа стартует по нажатию — это инструмент 2
ошибка
LaunchedEffect(Unit), когда тело читает меняющийся параметр
Заметка про загрузку вообще

Вариант выше рабочий и читаемый, но не единственный. Часто чище, когда решение «пора грузить» принимает сама ViewModel — через SavedStateHandle и flatMapLatest, либо через stateIn(WhileSubscribed(5_000)), где появление подписчика и есть сигнал. Тогда возврат на экран не порождает лишний запрос, а UI вообще не участвует в решении.

2. rememberCoroutineScope() — корутина в ответ на действие

Начнем с проблемы, ради которой он существует: composable-функция не suspend, а многие UI-операции — suspend.

Button(
    onClick = {
        snackbarHostState.showSnackbar(message = "Скопировано")   // не компилируется
    }
) { Text(text = "Скопировать") }

onClick — обычная лямбда, из нее нельзя вызвать suspend-функцию. Нужен скоуп. LaunchedEffect тут не подходит принципиально: он запускается сам при появлении на экране, а не в момент нажатия — по клику его никак не «вызвать».

val scope = rememberCoroutineScope()

Button(
    onClick = {
        scope.launch { snackbarHostState.showSnackbar(message = "Скопировано") }
    }
) { Text(text = "Скопировать") }

Почему именно remember-версия, а не свой скоуп

Скоуп создается один раз при входе в композицию и отменяется, когда composable из нее уходит. Ушел с экрана посреди анимации скролла или показа снекбара — корутина отменилась сама, без единой строки от тебя.

val scope = CoroutineScope(Dispatchers.Main)   // новый скоуп на каждой рекомпозиции,
                                               // никто его не отменяет — утечка

Внутри — remember плюс объект, реализующий тот самый RememberObserver из раздела 03: в onForgotten он вызывает cancel(). Тот же механизм, что у остальных эффектов.

Где он реально нужен

У UI-контроллеров Compose методы объявлены suspend — именно чтобы анимация доигрывала и отменялась вместе с экраном. Это и есть основные потребители скоупа:

CompanyScreen.kt — типичный набор сразу

@Composable
fun CompanyScreen(viewModel: CompanyViewModel = hiltViewModel()) {
    val scope = rememberCoroutineScope()
    val listState = rememberLazyListState()
    val sheetState = rememberModalBottomSheetState()
    val snackbarHostState = remember { SnackbarHostState() }
    val state by viewModel.state.collectAsStateWithLifecycle()

    Scaffold(
        snackbarHost = { SnackbarHost(snackbarHostState) },
        floatingActionButton = {
            FloatingActionButton(
                onClick = { scope.launch { listState.animateScrollToItem(index = 0) } }
            ) { Icon(painter = painterResource(R.drawable.ds_arrow_up), contentDescription = null) }
        }
    ) { padding ->
        LazyColumn(state = listState, modifier = Modifier.padding(padding)) {
            items(items = state.offers, key = { it.id }) { offer ->
                OfferRow(
                    offer = offer,
                    onDetailsClick = { scope.launch { sheetState.show() } },
                    onCopyCode = {
                        scope.launch { snackbarHostState.showSnackbar(message = "Код скопирован") }
                    }
                )
            }
        }
    }
}

Чего в него класть не надо

Сетевые запросы и бизнес-логику. По клику вызывается обычная функция ViewModel, а корутину она запускает у себя — в viewModelScope, который переживет и поворот экрана, и уход composable из композиции.

onClick = {
    scope.launch { repository.pay(amount = amount) }   // повернул экран — платеж отменился
}
onClick = { viewModel.pay(amount = amount) }           // обычный вызов, корутина внутри VM
Разделение в одну строку

Началось само, потому что экран появился — LaunchedEffect. Началось потому, что пользователь нажал, — rememberCoroutineScope. Работа переживает экран — вообще не UI-скоуп, а viewModelScope.

берем
из колбэка надо вызвать suspend-функцию UI-контроллера: снекбар, скролл, шторка, пейджер
не берем
работа начинается сама при появлении экрана; работа не должна умирать вместе с экраном
ошибка
scope.launch { } прямо в теле composable — кейс 3

3. DisposableEffect(keys) — есть что освободить

Единственный эффект с обязательной очисткой: без onDispose код не компилируется. Слушатели, ресиверы, коллбэки системных сервисов, флаги окна.

ConnectivityBanner.kt

@Composable
fun ConnectivityBanner(modifier: Modifier = Modifier) {
    val context = LocalContext.current
    var isOnline by remember { mutableStateOf(true) }

    DisposableEffect(context) {
        val manager = context.getSystemService(ConnectivityManager::class.java)
        val callback = object : ConnectivityManager.NetworkCallback() {
            override fun onAvailable(network: Network) { isOnline = true }
            override fun onLost(network: Network) { isOnline = false }
        }
        manager.registerDefaultNetworkCallback(callback)

        onDispose { manager.unregisterNetworkCallback(callback) }   // без этого — утечка
    }

    AnimatedVisibility(visible = !isOnline, modifier = modifier) {
        OfflineStub(text = "Нет соединения")
    }
}
берем
что-то регистрируется и обязано быть снято
не берем
освобождать нечего: пустой onDispose — признак неверного выбора
ошибка
ключ Unit при том, что тело читает меняющееся значение — кейс 12

4. rememberUpdatedState(value) — свежее значение без перезапуска

Кладет значение в state и переписывает его на каждом прогоне. Долгоживущий эффект читает всегда актуальное, но рестарта не получает.

AutoDismissBanner.kt

@Composable
fun AutoDismissBanner(
    text: String,
    onDismiss: () -> Unit,          // родитель пересоздает эту лямбду на каждом своем прогоне
    modifier: Modifier = Modifier
) {
    val currentOnDismiss by rememberUpdatedState(onDismiss)

    LaunchedEffect(Unit) {          // отсчет запускается ровно один раз
        delay(BANNER_VISIBLE_MILLIS)
        currentOnDismiss()          // вызовется та лямбда, что актуальна сейчас
    }

    Surface(modifier = modifier, color = MaterialTheme.colorScheme.secondaryContainer) {
        Text(text = text, modifier = Modifier.padding(16.dp))
    }
}

private const val BANNER_VISIBLE_MILLIS = 5_000L

Внутри — remember { mutableStateOf(value) }, значение которого переписывается при каждой рекомпозиции. Эффект держит ссылку на state, а не на само значение, поэтому перезапускать его незачем.

берем
эффект длинный, значение меняется, перезапускать нельзя
не берем
смена значения как раз и должна перезапускать эффект — тогда это ключ
ошибка
обернуть все подряд: эффект перестанет реагировать на то, на что должен

5. SideEffect { } — отдать значение наружу

Выполняется после каждой успешной композиции, ключей не имеет. Единственная задача: протолкнуть актуальное значение в объект, который про Compose ничего не знает.

@Composable
fun AnalyticsUser(user: User) {
    val analytics = LocalAnalytics.current

    SideEffect {
        analytics.setUserProperty(userId = user.id)   // объект живет вне композиции
    }
}
берем
внешнему объекту нужно свежее значение после каждой удачной композиции
не берем
нужна однократность или отмена
ошибка
любая тяжелая работа: главный поток, столько раз, сколько было композиций

6. produceState(initial, keys) — чужой источник превращается в состояние

Внутри — remember { mutableStateOf(initial) } плюс LaunchedEffect. Удобно для коллбэк-API и разовых suspend-вызовов, когда результат нужен прямо как State.

@Composable
fun rememberQrBitmap(payload: String): State<Bitmap?> =
    produceState<Bitmap?>(initialValue = null, key1 = payload) {
        value = withContext(Dispatchers.Default) {      // генерация тяжелая — уводим с main
            QrGenerator.generate(payload = payload)
        }
    }

@Composable
fun LoyaltyQr(payload: String, modifier: Modifier = Modifier) {
    val bitmap by rememberQrBitmap(payload = payload)

    if (bitmap == null) {
        QrPlaceholder(modifier = modifier)
    } else {
        Image(bitmap = bitmap!!.asImageBitmap(), contentDescription = null, modifier = modifier)
    }
}
Частая подмена

produceState вместо collectAsStateWithLifecycle для потока из ViewModel. Внутри LaunchedEffect, то есть привязка к композиции, а не к lifecycle: у свернутого приложения сбор продолжается. Кейс 9.

7. snapshotFlow { } — мост из состояния в корутину

Превращает чтение State в Flow. Подписывается на все состояния, прочитанные внутри блока, и присылает значение при изменении — с distinctUntilChanged по умолчанию.

OperationsScreen.kt

@Composable
fun OperationsScreen(viewModel: OperationsViewModel = hiltViewModel()) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    val listState = rememberLazyListState()

    LaunchedEffect(listState) {
        snapshotFlow { listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index }
            .filterNotNull()
            .distinctUntilChanged()
            .collect { lastVisible ->
                if (lastVisible >= state.items.lastIndex - PREFETCH_DISTANCE) {
                    viewModel.loadNextPage()
                }
            }
    }

    LazyColumn(state = listState) {
        items(items = state.items, key = { it.id }) { operation ->
            OperationRow(operation = operation)
        }
        if (state.isPaginating) {
            item { PaginationProgress() }
        }
    }
}

private const val PREFETCH_DISTANCE = 5
берем
реакция на изменение состояния нужна в корутине: пагинация, аналитика скролла, автосохранение
не берем
значение нужно для отрисовки — читай его прямо в теле
ошибка
положить состояние скролла в ключ эффекта — кейс 8

8. Lifecycle-эффекты — привязка к экрану, а не к композиции

Из androidx.lifecycle:lifecycle-runtime-compose. Закрывают дыру из раздела 02: композиция жива, пока приложение свернуто, а реагировать надо на onStart и onResume.

@Composable
fun ScannerScreen(viewModel: ScannerViewModel = hiltViewModel()) {
    // поток собирается только между onStart и onStop
    val state by viewModel.state.collectAsStateWithLifecycle()

    // камера включается на onResume и гасится на onPause
    LifecycleResumeEffect(Unit) {
        viewModel.startCamera()
        onPauseOrDispose { viewModel.stopCamera() }
    }

    ScannerContent(state = state)
}
ИнструментКогда
collectAsStateWithLifecycle() Дефолт для любого Flow из ViewModel
LifecycleEventEffect(ON_RESUME) Разовое действие на событие: обновить данные при возврате на экран
LifecycleResumeEffect { … onPauseOrDispose { } } Парное действие: включить на RESUME, выключить на PAUSE
repeatOnLifecycle(STARTED) Ручной сбор потока, когда нужен контроль над обработкой каждого элемента

07 Дерево решений

Что нужно сделать?
│
├─ отреагировать на клик, свайп, результат диалога
│     └─ rememberCoroutineScope().launch { }
│
├─ запустить работу, пока экран показан
│     ├─ зависит от параметра  → LaunchedEffect(параметр)
│     └─ ни от чего не зависит → LaunchedEffect(Unit)
│
├─ работа только на видимом экране, не в фоне
│     └─ collectAsStateWithLifecycle / LifecycleResumeEffect
│
├─ зарегистрировать слушателя, ресивер, флаг окна
│     └─ DisposableEffect(ключи) { … onDispose { снять } }
│
├─ отреагировать на изменение состояния внутри корутины
│     └─ snapshotFlow { … }.collect { }
│
├─ отдать значение объекту вне Compose
│     └─ SideEffect { }
│
├─ длинному эффекту нужен свежий колбэк без перезапуска
│     └─ rememberUpdatedState(значение)
│
└─ превратить чужой источник в State
      └─ produceState(initial, ключи)
Часть II

Двенадцать кейсов

Одна и та же схема в каждом: задача с экрана, код как его обычно пишут, что при этом видит пользователь, объяснение через механику из части I и правильный вариант. Кейсы независимы, можно читать вразнобой.

Кейс 1. Открыли заказ — надо загрузить данные

Экран деталей заказа. Данные грузятся при открытии. Из этого же экрана стрелками переключаются на соседний заказ, не выходя обратно в список.

Как пишут

OrderDetailsScreen.kt

@Composable
fun OrderDetailsScreen(
    orderId: Long,
    viewModel: OrderDetailsViewModel = hiltViewModel(),
    onBack: () -> Unit
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    LaunchedEffect(Unit) {
        viewModel.loadOrder(orderId = orderId)
    }

    Scaffold(
        topBar = {
            OrderTopBar(
                title = "Заказ №${state.number}",
                onBack = onBack,
                onPrevious = { viewModel.onPreviousOrder() },
                onNext = { viewModel.onNextOrder() }
            )
        }
    ) { padding ->
        OrderContent(
            items = state.items,
            total = state.total,
            status = state.status,
            onRepeat = { viewModel.repeatOrder() },
            modifier = Modifier.padding(padding)
        )
    }
}
Что видит пользователь
  • Открыл заказ №100 — все верно, данные загрузились
  • Нажал стрелку «следующий», в шапке появилось «Заказ №101»
  • Состав, сумма и статус остались от заказа №100
  • Нажал «Повторить заказ» — оформился не тот заказ
Почему

Смена orderId — это рекомпозиция, а не новое появление функции: группа в памяти композиции та же самая. Ключ Unit равен сам себе, значит рантайму нечего выбрасывать и нечего создавать заново (раздел 03, строка «ключи не изменились»). Корутина стартовала один раз, с orderId = 100, и это значение в ней так и осталось.

Как надо
LaunchedEffect(orderId) {
    viewModel.loadOrder(orderId = orderId)
}

Вариант надежнее — вообще убрать загрузку из UI. Тогда экран не решает, когда грузить, и повторный вход в композицию не порождает лишний запрос:

@HiltViewModel
class OrderDetailsViewModel @Inject constructor(
    savedStateHandle: SavedStateHandle,
    private val repository: OrderRepository
) : ViewModel() {

    private val orderId = savedStateHandle.getStateFlow(key = "orderId", initialValue = 0L)

    val state: StateFlow<OrderUiState> = orderId
        .filter { it != 0L }
        .flatMapLatest { id -> repository.observeOrder(id = id) }   // сменился id — новый поток
        .map { OrderUiState.map(order = it) }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = OrderUiState.EMPTY
        )
}
ПравилоВсе, что тело эффекта читает и что может измениться, обязано стоять в скобках.

Кейс 2. Отправить событие «экран показан» в аналитику

Продукт хочет знать, сколько раз открывали «Кошелек» и сколько карт при этом было у пользователя.

Как пишут

WalletScreen.kt

@Composable
fun WalletScreen(
    viewModel: WalletViewModel = hiltViewModel(),
    onCardClick: (Long) -> Unit
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    analytics.logScreen(screen = "wallet", cardsCount = state.cards.size)

    LazyColumn {
        items(items = state.cards, key = { it.id }) { card ->
            LoyaltyCardRow(card = card, onClick = { onCardClick(card.id) })
        }
    }
}
Что видит пользователь
  • Пользователь не видит ничего — и в этом коварство кейса
  • В отчете 40 000 показов «Кошелька» при 5 000 активных пользователей
  • Часть событий с cardsCount = 0: они ушли до того, как приехали данные
  • Конверсия «показ → тап по карте» падает вдвое, продукт делает неверный вывод
Почему

Тело выполняется столько раз, сколько было рекомпозиций: пришли карты — прогон, обновился баланс — прогон, снялся спиннер — прогон (раздел 01, первое свойство прогона). Гарантии «один вызов на один показ экрана» у тела нет и быть не может.

Как надо
@Composable
fun WalletScreen(
    viewModel: WalletViewModel = hiltViewModel(),
    onCardClick: (Long) -> Unit
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    LaunchedEffect(Unit) {                                   // ровно один раз на показ экрана
        analytics.logScreen(screen = "wallet")
    }

    LazyColumn {
        items(items = state.cards, key = { it.id }) { card ->
            LoyaltyCardRow(card = card, onClick = { onCardClick(card.id) })
        }
    }
}

Если в событии нужны данные, которые приезжают позже, ключом становится признак их готовности, а не сами данные:

LaunchedEffect(state.isLoaded) {
    if (state.isLoaded) {
        analytics.logScreen(screen = "wallet", cardsCount = state.cards.size)
    }
}

А если считать надо именно возвраты на экран, а не появление в композиции, — LifecycleEventEffect(Lifecycle.Event.ON_RESUME) { analytics.logScreen(…) }.

ПравилоГлагол в теле composable — ошибка. Тело описывает картинку; log, load, send, navigate в нем не живут.

Кейс 3. Обновить список компаний

Экран «Мои компании»: список подтягивается при открытии и по свайпу вниз.

Как пишут

CompaniesScreen.kt

@Composable
fun CompaniesScreen(viewModel: CompaniesViewModel = hiltViewModel()) {
    val scope = rememberCoroutineScope()
    val state by viewModel.state.collectAsStateWithLifecycle()

    scope.launch { viewModel.refresh() }              // «пусть обновится при открытии»

    PullToRefreshBox(
        isRefreshing = state.isRefreshing,
        onRefresh = { scope.launch { viewModel.refresh() } }
    ) {
        LazyColumn {
            items(items = state.items, key = { it.id }) { company ->
                CompanyRow(company = company)
            }
        }
    }
}
Что видит пользователь
  • Экран открылся, пошла загрузка
  • Индикатор не останавливается: каждый ответ дает рекомпозицию, а она — новый запрос
  • Список дергается, сервер получает десятки одинаковых запросов в секунду
  • Ушел с экрана — часть запросов еще какое-то время висит
Почему

rememberCoroutineScope дает скоуп, но не решает, когда запускать корутину. Строка scope.launch { } — обычная строка тела, она выполняется на каждом прогоне и добавляет еще одну корутину. Получается положительная обратная связь: запрос → новые данные → рекомпозиция → запрос.

Как надо
@Composable
fun CompaniesScreen(viewModel: CompaniesViewModel = hiltViewModel()) {
    val scope = rememberCoroutineScope()
    val state by viewModel.state.collectAsStateWithLifecycle()

    LaunchedEffect(Unit) { viewModel.refresh() }      // само, при появлении экрана

    PullToRefreshBox(
        isRefreshing = state.isRefreshing,
        onRefresh = { scope.launch { viewModel.refresh() } }   // по жесту пользователя
    ) {
        LazyColumn {
            items(items = state.items, key = { it.id }) { company ->
                CompanyRow(company = company)
            }
        }
    }
}
ПравилоrememberCoroutineScope — только внутри колбэков. Само стартующее — LaunchedEffect.

Кейс 4. Таймер «Запросить код повторно»

Экран ввода кода из SMS. Шестьдесят секунд идет отсчет, потом кнопка становится активной и родителю сообщается, что можно запрашивать код заново.

Как пишут

ResendTimer.kt

@Composable
fun ResendTimer(
    seconds: Int,
    onFinished: () -> Unit,
    modifier: Modifier = Modifier
) {
    var left by remember { mutableIntStateOf(seconds) }

    LaunchedEffect(onFinished) {              // «зависимость же — колбэк»
        while (left > 0) {
            delay(1_000)
            left--
        }
        onFinished()
    }

    Text(
        text = "Запросить повторно через $left с",
        style = MaterialTheme.typography.bodyMedium,
        modifier = modifier
    )
}

Родитель — обратите внимание на лямбду

ResendTimer(
    seconds = 60,
    onFinished = { viewModel.onResendAvailable() }   // новый объект на каждом прогоне родителя
)
Что видит пользователь
  • Отсчет пошел: 60, 59, 58…
  • Число замирает или откатывается назад, кнопка не активируется никогда
  • Чем чаще перерисовывается родитель, тем сильнее отстает таймер
Почему

Лямбда, захватывающая viewModel, — новый объект на каждом прогоне родителя, поэтому ключ «изменился». Рантайм забывает старый эффект (отменяет корутину прямо посреди delay) и запускает новый (раздел 05, строка «нестабильный ключ»). Отсчет начинается сначала, а left при этом уже уменьшился — отсюда рваное поведение.

Сравни с кейсом 1: там ключа не хватало, здесь ключ лишний и вдобавок нестабильный. Механизм один и тот же — сравнение через equals.

Как надо
@Composable
fun ResendTimer(
    seconds: Int,
    onFinished: () -> Unit,
    modifier: Modifier = Modifier
) {
    var left by rememberSaveable { mutableIntStateOf(seconds) }   // переживет поворот
    val currentOnFinished by rememberUpdatedState(onFinished)     // свежий колбэк без рестарта

    LaunchedEffect(seconds) {                                     // рестарт только при новом запросе кода
        while (left > 0) {
            delay(1_000)
            left--
        }
        currentOnFinished()
    }

    Text(
        text = "Запросить повторно через $left с",
        style = MaterialTheme.typography.bodyMedium,
        modifier = modifier
    )
}
ПравилоЛямбда в ключах — почти всегда ошибка. Нужен свежий колбэк без перезапуска — rememberUpdatedState.

Кейс 5. Подписка на сканер

Экран сканирования QR: пока он открыт, слушаем результаты сканера и отдаем код наверх.

Как пишут

ScannerScreen.kt

@Composable
fun ScannerScreen(
    scanner: BarcodeScanner,
    onCode: (String) -> Unit,
    onClose: () -> Unit
) {
    LaunchedEffect(scanner) {
        scanner.addListener { code -> onCode(code) }
    }

    Box(modifier = Modifier.fillMaxSize()) {
        CameraPreview(modifier = Modifier.matchParentSize())
        ScannerOverlay(onClose = onClose)
    }
}
Что видит пользователь
  • Первый заход: отсканировал — сработало один раз, все хорошо
  • Вышел назад, зашел снова, отсканировал
  • Код обработан дважды: два перехода, два запроса, двойное списание бонусов
  • На пятый заход — пять срабатываний; в логах ошибки на уже закрытом экране
Почему

Корутину рантайм отменяет сам (onForgotten из раздела 03), а регистрацию слушателя — нет: addListener уже выполнился, и сканер держит ссылку на лямбду вместе со всем, что она захватила. Отмена корутины на это не влияет никак. Каждое появление экрана добавляет слушателя, старые продолжают жить — это утечка в чистом виде.

Как надо
@Composable
fun ScannerScreen(
    scanner: BarcodeScanner,
    onCode: (String) -> Unit,
    onClose: () -> Unit
) {
    val currentOnCode by rememberUpdatedState(onCode)     // лямбда свежая, подписка стабильная

    DisposableEffect(scanner) {
        val listener = ScanListener { code -> currentOnCode(code) }
        scanner.addListener(listener)
        onDispose { scanner.removeListener(listener) }    // компилятор не даст забыть
    }

    Box(modifier = Modifier.fillMaxSize()) {
        CameraPreview(modifier = Modifier.matchParentSize())
        ScannerOverlay(onClose = onClose)
    }
}

Признак выбора простой: что-то регистрируется — значит должно быть снято. Обратное тоже верно: пустой onDispose означает, что нужен был LaunchedEffect.

ПравилоНа каждый add, register, subscribe — свой remove в onDispose.

Кейс 6. Снекбар с ошибкой оплаты

Оплата не прошла — показать снекбар с текстом ошибки. Один раз.

Как пишут

CheckoutViewModel.kt

@HiltViewModel
class CheckoutViewModel @Inject constructor(
    private val repository: CheckoutRepository

        }

CheckoutScreen.kt

@Composable
fun CheckoutScreen(viewModel: CheckoutViewModel = hiltViewModel()) {
    val snackbarHostState = remember { SnackbarHostState() }
    val error by viewModel.errorMessage.collectAsStateWithLifecycle()

    LaunchedEffect(error) {
        error?.let { snackbarHostState.showSnackbar(message = it) }
    }

    Scaffold(snackbarHost = { SnackbarHost(snackbarHostState) }) { padding ->
        CheckoutContent(onPay = { viewModel.pay(amount = it) }, modifier = Modifier.padding(padding))
    }

Что видит пользователь
  • Оплата не прошла, снекбар показался — пока правильно
  • Повернул телефон, чтобы удобнее ввести данные карты
  • Снекбар с той же ошибкой выезжает второй раз
  • Свернул и вернулся — снова та же ошибка, хотя ничего не нажимал
Почему

Состояние и событие ведут себя противоположно: состояние обязано пережить поворот экрана, событие обязано его не пережить. В StateFlow лежит последнее значение, и новая композиция читает его как ни в чем не бывало — для нее это «текущая ошибка», а не «ошибка, которую уже показали».

Как надо

CheckoutViewModel.kt — событие гасится

data class CheckoutUiState(
    val isPaying: Boolean = false,
    val message: String? = null          // null = показывать нечего
)

@HiltViewModel
class CheckoutViewModel @Inject constructor(
    private val repository: CheckoutRepository
) : ViewModel() {

    private val _state = MutableStateFlow(CheckoutUiState())
    val state: StateFlow<CheckoutUiState> = _state.asStateFlow()

    fun pay(amount: Long) {
        viewModelScope.launch {
            _state.update { it.copy(isPaying = true) }
            runCatching { repository.pay(amount = amount) }
                .onFailure { error ->
                    ensureActive()
                    _state.update { it.copy(isPaying = false, message = error.messageOrDefault()) }
                }
        }
    }

    fun onMessageShown() {
        _state.update { it.copy(message = null) }      // событие погашено
    }
}

CheckoutScreen.kt

LaunchedEffect(state.message) {
    val message = state.message ?: return@LaunchedEffect
    snackbarHostState.showSnackbar(message = message)
    viewModel.onMessageShown()
}

Альтернатива — Channel с receiveAsFlow: он не хранит последнее значение и буферизует событие, пока UI не начал слушать. Оба варианта рабочие, важно одно: после обработки событие должно перестать существовать.

ПравилоРазовое событие живет до первой обработки. Хранится как состояние — гасится явно.

Кейс 7. Переход на экран успеха после оплаты

Оплата прошла — уводим пользователя на экран «Готово».

Как пишут
@Composable
fun PaymentScreen(
    navController: NavController,
    viewModel: PaymentViewModel = hiltViewModel()
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    LaunchedEffect(state.isPaid) {
        if (state.isPaid) {
            navController.navigate(route = Routes.Success)
        }
    }

    PaymentContent(state = state, onPay = { viewModel.pay() })
}
Что видит пользователь
  • Оплата прошла, открылся экран «Готово»
  • Нажал «Назад», ожидая вернуться в каталог
  • Снова экран «Готово»: в стеке их два
  • Иногда переход срабатывает после того, как пользователь уже ушел сам
Почему

Два наложившихся эффекта. Первое: флаг isPaid остается в состоянии и после перехода, поэтому возврат на экран пересоздает композицию и эффект отрабатывает снова. Второе: между отправкой события и его обработкой экран мог смениться, и navigate выполняется уже из чужого места графа.

Как надо
@Composable
fun PaymentScreen(
    onPaid: (orderId: Long) -> Unit,          // экран не знает про navController
    viewModel: PaymentViewModel = hiltViewModel()
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    LaunchedEffect(state.paidOrderId) {
        val orderId = state.paidOrderId ?: return@LaunchedEffect
        onPaid(orderId)
        viewModel.onPaidHandled()             // событие погашено
    }

    PaymentContent(state = state, onPay = { viewModel.pay() })
}

Граф навигации — решение принимается здесь

composable<Routes.Payment> {
    PaymentScreen(
        onPaid = { orderId ->
            if (navController.currentDestination?.hasRoute<Routes.Payment>() == true) {
                navController.navigate(route = Routes.Success(orderId = orderId)) {
                    popUpTo<Routes.Payment> { inclusive = true }   // назад на оплату не возвращаемся
                }
            }
        }
    )
}

Проверка текущего destination перед переходом — то же правило, что действует в нашем XML-коде, и в Compose оно не отменяется.

ПравилоНавигация из эффекта — только с гашением события и проверкой, что экран все еще тот.

Кейс 8. Подгрузка следующей страницы операций

История операций, постраничная загрузка: доскроллил почти до конца — грузим следующую страницу.

Как пишут
@Composable
fun OperationsScreen(viewModel: OperationsViewModel = hiltViewModel()) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    val listState = rememberLazyListState()

    LaunchedEffect(listState.firstVisibleItemIndex) {
        if (listState.firstVisibleItemIndex > state.items.size - 5) {
            viewModel.loadNextPage()
        }
    }

    LazyColumn(state = listState) {
        items(items = state.items, key = { it.id }) { operation ->
            OperationRow(operation = operation)
        }
    }
}
Что видит пользователь
  • Скроллит список — на глаз работает
  • Прокрутка подтормаживает: эффект перезапускается на каждый сдвиг строки
  • Быстрым свайпом можно проскочить порог, и подгрузка не срабатывает вовсе
  • Иногда уходят два одинаковых запроса подряд
Почему

Состояние скролла в ключе — это перезапуск эффекта на каждое изменение, десятки раз в секунду (раздел 05, «избыток»). Обратный вариант, LaunchedEffect(Unit) с чтением индекса внутри, не работает по другой причине: корутина не подписывается на состояние. Композиция наблюдает за State, корутина — нет.

Как надо
LaunchedEffect(listState) {
    snapshotFlow { listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index }
        .filterNotNull()
        .distinctUntilChanged()
        .collect { lastVisible ->
            if (lastVisible >= state.items.lastIndex - PREFETCH_DISTANCE) {
                viewModel.loadNextPage()      // ViewModel сама игнорирует повторный вызов,
            }                                 // пока страница уже грузится
        }
}

snapshotFlow подписывается на чтения внутри своего блока и присылает значение при изменении, уже с distinctUntilChanged. Эффект при этом стартует один раз.

ПравилоРеакция на изменение состояния внутри корутины — snapshotFlow, а не ключ эффекта.

Кейс 9. Баланс в шапке кошелька

Баланс приходит потоком из ViewModel и должен обновляться в реальном времени, пока пользователь смотрит на экран.

Как пишут
@Composable
fun BalanceHeader(viewModel: WalletViewModel, modifier: Modifier = Modifier) {
    val balance by produceState(initialValue = 0L) {
        viewModel.balanceFlow.collect { value = it }
    }

    Text(
        text = balance.formatAsPoints(),
        style = MaterialTheme.typography.headlineSmall,
        modifier = modifier
    )
}

Тот же баг, но в более привычной записи:

val balance by viewModel.balanceFlow.collectAsState(initial = 0L)
Что видит пользователь
  • На экране все верно, баланс живой
  • Свернул приложение и забыл о нем на час
  • Батарея садится быстрее обычного, в статистике заметный трафик
  • Сокет живет в фоне, сервер держит соединение, аналитика считает активность
Почему

Внутри produceState — remember плюс LaunchedEffect, то есть привязка к композиции. А композиция никуда не девается, когда приложение свернули: экран по-прежнему в графе, функция по-прежнему в композиции, корутина работает. Жизненный цикл экрана и присутствие в композиции — разные вещи (раздел 02), и эффекты знают только про второе.

Как надо
@Composable
fun BalanceHeader(viewModel: WalletViewModel, modifier: Modifier = Modifier) {
    val balance by viewModel.balance.collectAsStateWithLifecycle()   // только между onStart и onStop

    Text(
        text = balance.formatAsPoints(),
        style = MaterialTheme.typography.headlineSmall,
        modifier = modifier
    )
}

WalletViewModel.kt — вторая половина решения

val balance: StateFlow<Long> = repository.observeBalance()
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),   // свернули — через 5 с источник отключился
        initialValue = 0L
    )

Пять секунд задержки нужны, чтобы поворот экрана не рвал подписку: подписчик исчезает и появляется снова быстрее этого срока. produceState остается для источников без своего адаптера — коллбэк-API, разовый suspend-вызов.

ПравилоЛюбой Flow из ViewModel — collectAsStateWithLifecycle. Без вариантов.

Кейс 10. Отдать значение объекту, который не знает про Compose

В аналитике должен стоять идентификатор пользователя, чтобы события уходили с правильным атрибутом.

Как пишут
@Composable
fun App(user: User) {
    LaunchedEffect(user.id) {
        analytics.setUserProperty(userId = user.id)
    }
    AppNavHost(user = user)
}
В чем разница

Катастрофы нет: код рабочий. Но LaunchedEffect — это корутина с отменой и перезапуском, а задача другая: протолкнуть свежее значение наружу после того, как композиция успешно применилась. Для нее есть SideEffect — без корутины, без ключей, ровно один вызов на каждую удачную композицию (раздел 04).

Как надо
@Composable
fun App(user: User) {
    SideEffect {
        analytics.setUserProperty(userId = user.id)
    }
    AppNavHost(user = user)
}
А вот это уже настоящая ошибка
SideEffect {
    prefs.edit().putString("last_screen", screen).commit()   // запись на диск, main thread,
}                                                            // на каждой композиции

Тело SideEffect выполняется на главном потоке столько раз, сколько было композиций. Все, что тяжелее присваивания, туда класть нельзя: ни диск, ни сеть, ни разбор json.

ПравилоSideEffect — только легкая передача значения наружу. Нужна отмена или однократность — LaunchedEffect.

Кейс 11. Считать показы баннеров в ленте

Лента с баннерами. Нужно знать, какие баннеры пользователь реально видел, — по одному событию на баннер.

Как пишут
@Composable
fun FeedScreen(
    banners: List<Banner>,
    onBannerShown: (Long) -> Unit,
    onBannerClick: (Long) -> Unit
) {
    LazyColumn {
        items(items = banners, key = { it.id }) { banner ->
            LaunchedEffect(banner.id) {
                onBannerShown(banner.id)
            }
            BannerCard(banner = banner, onClick = { onBannerClick(banner.id) })
        }
    }
}
Что видит пользователь
  • Пролистал ленту вниз и обратно вверх пару раз
  • У баннера накрутилось шесть показов вместо одного
  • Рекламодателю уходит завышенная статистика, отчеты расходятся с бэкендом
Почему

Элемент, уехавший за пределы экрана, уходит из композиции вместе со своими эффектами, а при обратном скролле входит в нее заново (раздел 02). Для LaunchedEffect это полноценное новое появление: onRemembered, старт корутины. «Вход в композицию» и «пользователь увидел» — разные события, и в списках они расходятся сильнее всего.

Как надо
@Composable
fun FeedScreen(
    banners: List<Banner>,
    viewModel: FeedViewModel = hiltViewModel(),
    onBannerClick: (Long) -> Unit
) {
    val listState = rememberLazyListState()

    LaunchedEffect(listState) {
        snapshotFlow { listState.layoutInfo.visibleItemsInfo.map { it.key } }
            .distinctUntilChanged()
            .collect { visibleKeys -> viewModel.onBannersVisible(keys = visibleKeys) }
    }

    LazyColumn(state = listState) {
        items(items = banners, key = { it.id }) { banner ->
            BannerCard(banner = banner, onClick = { onBannerClick(banner.id) })
        }
    }
}

FeedViewModel.kt — однократность живет здесь

private val reportedBanners = mutableSetOf<Long>()

fun onBannersVisible(keys: List<Any>) {
    keys.filterIsInstance<Long>()
        .filter { reportedBanners.add(it) }     // add вернет false, если уже отправляли
        .forEach { analytics.bannerShown(bannerId = it) }
}

Общий принцип: то, что должно случиться один раз за сессию, не может жить в эффекте элемента списка — его жизненный цикл слишком короткий.

ПравилоЭффект внутри item { } повторяется при каждом появлении элемента. Однократность обеспечивается снаружи.

Кейс 12. Экран не должен гаснуть во время игры

Пока идет раунд, экран не засыпает. Раунд начинается и заканчивается, экран при этом остается открытым.

Как пишут
@Composable
fun GameScreen(viewModel: GameViewModel = hiltViewModel()) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    val window = (LocalContext.current as Activity).window

    DisposableEffect(Unit) {
        if (state.isPlaying) window.addFlags(FLAG_KEEP_SCREEN_ON)
        onDispose { window.clearFlags(FLAG_KEEP_SCREEN_ON) }
    }

    GameContent(state = state, onStart = { viewModel.startRound() })
}
Что видит пользователь
  • Зашел на экран, раунд еще не начался
  • Начал играть
  • Экран гаснет посреди раунда: флаг не выставился, при входе isPlaying был false
  • Обратный случай — вошел во время раунда, раунд кончился, а экран продолжает гореть и жрет батарею
Почему

Тело читает state.isPlaying, а в ключах его нет. Эффект отработал один раз при входе и больше никогда. Тот же механизм, что в кейсе 1, но заметить труднее: isPlaying — не параметр функции, а вложенное поле состояния, и глаз за него не цепляется.

Как надо
DisposableEffect(state.isPlaying) {
    if (state.isPlaying) window.addFlags(FLAG_KEEP_SCREEN_ON)
    onDispose { window.clearFlags(FLAG_KEEP_SCREEN_ON) }
}

Порядок при смене ключа: сначала onDispose старого захода, потом тело нового (раздел 04). Флаг не задвоится и не потеряется.

ПравилоПроверка на ревью в одно движение: прочитать тело эффекта и сверить каждое изменяемое имя со скобками — включая поля состояния.

Чеклист ревью

  1. В теле composable нет глаголов: только описание UI и вычисление значений для него.
  2. У каждого эффекта в ключах — все меняющиеся имена из тела, включая поля состояния.
  3. Ключи стабильны: не лямбда, не собранный по месту объект, не список.
  4. Все, что регистрируется, снимается в onDispose; пустого onDispose нет.
  5. Потоки из ViewModel собираются через collectAsStateWithLifecycle.
  6. Разовые события гасятся после обработки; навигация защищена проверкой destination.
  7. Реакция на состояние внутри корутины — через snapshotFlow.
  8. rememberCoroutineScope используется только внутри колбэков.
  9. Эффекты внутри элементов списка осознаны: вход в композицию у них повторяется.
  10. Тяжелая работа внутри эффекта уходит с главного потока.
Если запоминать одно

Эффект — объект в памяти композиции, а его ключи — ключи remember. Отсюда выводится каждый кейс выше: ключ не изменился — эффект работает со старым значением; изменился — старое отменяется и запускается заново; объект ушел из композиции — отмена. Все остальное это выбор инструмента под вопрос «сколько раз это должно случиться и что будет, когда экран уйдет».
