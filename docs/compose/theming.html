Часть I

Механика: как устроена тема

Восемь разделов. К концу будет понятно, что тема — это не набор констант, а три системы, разложенные по дереву композиции, и почему свои токены добавляются не в нее, а рядом.

01 Что такое тема

MaterialTheme — не стиль и не набор констант. Это функция, которая кладет три объекта в дерево композиции, чтобы любой компонент ниже мог их прочитать, не получая параметром.

@Composable
fun MaterialTheme(
    colorScheme: ColorScheme = MaterialTheme.colorScheme,
    shapes: Shapes = MaterialTheme.shapes,
    typography: Typography = MaterialTheme.typography,
    content: @Composable () -> Unit
) {
    CompositionLocalProvider(
        LocalColorScheme provides colorScheme,       // цвета
        LocalShapes provides shapes,                 // формы
        LocalTypography provides typography,         // шрифты
        LocalContentColor provides colorScheme.onSurface,
        LocalTextSelectionColors provides selectionColors,
        …
    ) {
        ProvideTextStyle(value = typography.bodyLarge, content = content)
    }
}
MaterialTheme
├─ colorScheme    29 именованных слотов: primary, surface, error и их on-пары
├─ typography     15 стилей: display / headline / title / body / label × Large, Medium, Small
└─ shapes          5 форм: extraSmall … extraLarge

читаются в любом месте ниже по дереву:
    MaterialTheme.colorScheme.primary
    MaterialTheme.typography.titleMedium
    MaterialTheme.shapes.medium
Material 3 Expressive

В свежих версиях material3 рядом с MaterialTheme появился MaterialExpressiveTheme — та же идея, но систем четыре: к цветам, типографике и формам добавлена motionScheme. Она задает пружины анимаций на весь экран: вариант standard — сдержанные переходы, expressive — с заметным перелетом. Плюс расширенная библиотека форм и морфинг между ними.

MaterialExpressiveTheme(
    colorScheme = AppColorScheme,
    motionScheme = MotionScheme.expressive(),   // четвертая система: пружины анимаций
    shapes = AppShapes,
    typography = AppTypography,
    content = content
)

Отсюда первое следствие: тема действует на поддерево, а не на приложение. Один MaterialTheme внутри другого перекрывает значения только для своего блока — так делают темные шапки на светлом экране. И второе: если composable оказался вне MaterialTheme, он не упадет, а возьмет схему по умолчанию — фиолетовую (кейс 4).

02 Цветовая схема: слоты, а не цвета

В ColorScheme нет «синего» и «серого» — есть роли. Каждая роль отвечает на вопрос «что этим красят», и у большинства есть парный on-цвет: то, чем писать поверх.

ГруппаСлотыЧем красят
Основнаяprimary, onPrimary, primaryContainer, onPrimaryContainer главные действия: залитая кнопка, активный переключатель, FAB
Вторичнаяsecondary…, tertiary… второстепенные акценты, чипы, выделения
Поверхности surface, onSurface, onSurfaceVariant, surfaceContainerLowest … High, Highest фоны экрана, карточек, шторок, панелей
Ошибкиerror, onError, errorContainer, onErrorContainer валидация, деструктивные действия
Границыoutline, outlineVariant рамки полей, разделители
Прочееscrim, inverseSurface, surfaceTint затемнение под диалогом, снекбар, тональная высота

Пары — главный механизм читаемости. Функция contentColorFor(color) по цвету фона находит парный цвет содержимого, и именно ее зовет Surface:

contentColorFor(colorScheme.primary)          // → onPrimary
contentColorFor(colorScheme.errorContainer)   // → onErrorContainer
contentColorFor(Color(0xFF102A43))            // → Color.Unspecified: пары нет
Правило пары

Фон берется из схемы — цвет текста поверх него берется из парного слота, и обычно его вообще не надо указывать. Смешивать пары нельзя: фон primaryContainer с текстом onSurface может оказаться нечитаемым в одной из тем (кейс 2).

Шкала поверхностей в Material 3 заменила ступени высоты: раньше слой поднимали тенью, теперь различают цветом.

surfaceContainerLowest   ← самый дальний слой: фон под карточками
surfaceContainerLow
surfaceContainer         ← обычная карточка
surfaceContainerHigh     ← карточка внутри карточки, шторка
surfaceContainerHighest  ← ближайший слой: активная строка, выделение

surfaceDim / surfaceBright   крайние значения фона: темный и светлый край шкалы
Важное отличие от тональной высоты

Слоты surfaceContainer* — фиксированные цвета схемы, и tonalElevation на них не влияет. Компоненты Material, которые раньше вычисляли фон через Surface плюс тональную высоту, сейчас берут эти роли напрямую. Практический вывод: различать слои нужно слотами, а не подбором высоты (кейс 8).

03 Светлая и темная

Схем всегда две, и переключение — это выбор объекта, а не пересчет цветов.

private val LightColors = lightColorScheme(
    primary = Purple40,
    onPrimary = Color.White,
    primaryContainer = Purple90,
    surface = Grey99,
    onSurface = Grey10,
    error = Red40
)

private val DarkColors = darkColorScheme(
    primary = Purple80,            // в темной теме основной цвет светлее, а не темнее
    onPrimary = Purple20,
    primaryContainer = Purple30,
    surface = Grey10,
    onSurface = Grey90,
    error = Red80
)

@Composable
fun AppTheme(
    darkTheme: Boolean = isSystemInDarkTheme(),
    content: @Composable () -> Unit
) {
    MaterialTheme(
        colorScheme = if (darkTheme) DarkColors else LightColors,
        typography = AppTypography,
        shapes = AppShapes,
        content = content
    )
}

Незаданные слоты lightColorScheme и darkColorScheme заполняют базовыми значениями Material — поэтому схема всегда полная, и композиция не падает, если про какой-то слот забыли. Она просто окажется фиолетовой в этом месте.

Динамические цвета

val colorScheme = when {
    dynamicColor && Build.VERSION.SDK_INT >= Build.VERSION_CODES.S -> {
        val context = LocalContext.current
        if (darkTheme) dynamicDarkColorScheme(context) else dynamicLightColorScheme(context)
    }
    darkTheme -> DarkColors
    else -> LightColors
}

Схема строится из обоев пользователя. Это уместно для приложений без сильного бренда — и вредно там, где фирменный цвет часть узнаваемости: включив динамику, ты отдаешь палитру системе (кейс 3).

04 Типографика

Пятнадцать стилей: пять ролей по три размера. Роль выбирается по назначению текста, а не по нужному кеглю.

РольРазмерыДля чего
displayLarge / Medium / Smallкрупные числа и промо-заголовки, редко
headlineLarge / Medium / Smallзаголовок экрана
titleLarge / Medium / Smallзаголовок блока, строки списка
bodyLarge / Medium / Smallосновной текст; bodyLarge — значение по умолчанию
labelLarge / Medium / Smallподписи кнопок, чипов, полей
private val Inter = FontFamily(
    Font(R.font.inter_regular, FontWeight.Normal),
    Font(R.font.inter_medium, FontWeight.Medium),
    Font(R.font.inter_semibold, FontWeight.SemiBold)
)

val AppTypography = Typography(
    headlineSmall = TextStyle(
        fontFamily = Inter,
        fontWeight = FontWeight.SemiBold,
        fontSize = 20.sp,           // именно sp: масштабируется системной настройкой шрифта
        lineHeight = 26.sp
    ),
    bodyMedium = TextStyle(
        fontFamily = Inter,
        fontWeight = FontWeight.Normal,
        fontSize = 15.sp,
        lineHeight = 20.sp
    ),
    labelLarge = TextStyle(fontFamily = Inter, fontWeight = FontWeight.Medium, fontSize = 14.sp)
)

Единицы имеют значение: sp учитывает системную настройку размера шрифта, dp — нет. Текст в dp — это экран, который не читается людьми, увеличившими шрифт в настройках (кейс 7).

val AppShapes = Shapes(

    small = RoundedCornerShape(8.dp),
    medium = RoundedCornerShape(12.dp),     // карточки
    large = RoundedCornerShape(16.dp),      // шторки, крупные блоки

Кроме пяти базовых форм в M3 Expressive добавилась библиотека готовых фигур — скругленные квадраты, фестоны, звезды — и анимированный морфинг между ними. Это инструмент для акцентных элементов: аватаров, иконок состояния, индикаторов загрузки, — а не для карточек и кнопок, которым по-прежнему хватает Shapes.

06 Как компоненты читают тему

Компонент не берет цвет напрямую из схемы — между ними два слоя, и знание про них объясняет, почему «текст сам правильного цвета».

MaterialTheme
   │  colorScheme.surface, onSurface, typography.bodyLarge
   ▼
Surface / Button / Card
   │  contentColorFor(цвет фона) → LocalContentColor
   │  ProvideTextStyle(нужный стиль)
   ▼
Text, Icon
      читают LocalContentColor и LocalTextStyle, если им ничего не передали
СлойЧто делает
MaterialTheme.colorSchemeхранит палитру ролей
*Defaults ButtonDefaults, CardDefaults, TextFieldDefaults: переводят роли в наборы состояний компонента
LocalContentColorцвет содержимого текущей поверхности
LocalTextStyleстиль текста, действующий по умолчанию

Практический вывод: у большинства Text и Icon не должно быть ни color, ни style. Указывать их нужно там, где текст сознательно отличается от окружения — например, второстепенная подпись onSurfaceVariant.

07 Своя дизайн-система поверх

Рано или поздно появляются токены, которых в Material нет: отступы, свои семантические цвета (успех, предупреждение, бренд), высоты элементов. Официальная дока описывает три стратегии, и выбирают между ними один раз на проект.

СтратегияЧто происходитКогда
Расширить тему MaterialTheme остается, рядом свои CompositionLocal с дополнительными токенами дефолт: дизайн-система близка к Material, нужны свои цвета и отступы
Заменить часть систем своя типографика или своя палитра, остальное берется из Material фирменные шрифты и цвета при стандартных компонентах
Своя тема целиком ни MaterialTheme, ни его компонентов: свои CompositionLocal и своя библиотека дизайн-система принципиально не Material; готовые компоненты все равно придется переписать

Чего делать не стоит ни в одной из них — выкручивать существующие токены под чужой смысл: класть цвет успеха в tertiary, а отступы в shapes. Нет слота для понятия — значит тему расширяют, а не переосмысляют (кейс 5).

@Immutable
data class AppColors(
    val success: Color,
    val warning: Color,
    val brand: Color,
    val onBrand: Color
)

@Immutable
data class AppSpacing(
    val xs: Dp = 4.dp,
    val s: Dp = 8.dp,
    val m: Dp = 16.dp,
    val l: Dp = 24.dp
)

val LocalAppColors = staticCompositionLocalOf<AppColors> { error("AppColors not provided") }
val LocalAppSpacing = staticCompositionLocalOf { AppSpacing() }

@Composable
fun AppTheme(darkTheme: Boolean = isSystemInDarkTheme(), content: @Composable () -> Unit) {
    val appColors = if (darkTheme) DarkAppColors else LightAppColors

    CompositionLocalProvider(
        LocalAppColors provides appColors,
        LocalAppSpacing provides AppSpacing()
    ) {
        MaterialTheme(
            colorScheme = if (darkTheme) DarkColors else LightColors,
            typography = AppTypography,
            shapes = AppShapes,
            content = content
        )
    }
}

// короткий доступ: AppTheme.colors.success, AppTheme.spacing.m
object AppTheme {
    val colors: AppColors
        @Composable get() = LocalAppColors.current
    val spacing: AppSpacing
        @Composable get() = LocalAppSpacing.current
}
ФабрикаКогда
staticCompositionLocalOf значение меняется редко — тема, отступы. При смене перезапускается все поддерево
compositionLocalOf значение меняется часто. Перезапускаются только те функции, что его читают

Для темы почти всегда static: смена темы — редкое событие, зато чтение дешевле, потому что рантайм не отслеживает читателей. И обязательный @Immutable на классе токенов: без него Compose считает тип нестабильным и перестает пропускать рекомпозиции у всего, что его принимает.

08 Превью и тесты

@Preview(name = "Светлая")

@Preview(name = "Крупный шрифт", fontScale = 2f)
@Composable
private fun GiftCardPreview() {

Три превью на один компонент ловят три разных класса ошибок: захардкоженные цвета, нечитаемые пары и верстку, рассыпающуюся при увеличенном шрифте. Дешевле, чем гонять сборку на устройстве.

Часть II

Восемь кейсов

Задача, код как его пишут, что видит пользователь, объяснение через разделы части I и правильный вариант.

Кейс 1. Хардкод цвета

Карточка статуса заказа: серый фон, темный текст — как в макете.

Как пишут
Surface(
    color = Color(0xFFF5F5F5),
    shape = RoundedCornerShape(12.dp)
) {
    Column(modifier = Modifier.padding(16.dp)) {
        Text(text = order.status, color = Color(0xFF212121))
        Text(text = order.date, color = Color(0xFF9E9E9E))
    }
}
Что видит пользователь
  • В светлой теме все как на макете
  • В темной — светло-серая плашка посреди темного экрана, как дырка
  • Текст на ней темный, но сама карточка теперь ярче фона приложения
  • После обновления дизайн-системы серый поменялся везде, кроме этого места
Почему

Значение Color(0xFFF5F5F5) не участвует ни в какой теме: оно одинаково в обеих. Схема — это набор ролей, которые меняются вместе (раздел 02), а литерал из нее выпадает.

Как надо
Surface(
    color = MaterialTheme.colorScheme.surfaceContainer,     // роль, а не цвет
    shape = MaterialTheme.shapes.medium
) {
    Column(modifier = Modifier.padding(16.dp)) {
        Text(text = order.status)                            // onSurface придет сам
        Text(text = order.date, color = MaterialTheme.colorScheme.onSurfaceVariant)
    }
}
ПравилоЛитерал Color(0x…) допустим ровно в одном месте — в файле палитры, откуда собираются схемы. В экранном коде его быть не должно.

Кейс 2. Пары цветов перепутаны

Блок с предупреждением: фон выделенный, текст поверх него.

Как пишут
Surface(color = MaterialTheme.colorScheme.errorContainer) {
    Text(
        text = "Не хватает бонусов",
        color = MaterialTheme.colorScheme.onSurface,      // цвет из чужой пары
        modifier = Modifier.padding(16.dp)
    )
}
Что видит пользователь
  • В светлой теме текст читается, разница почти незаметна
  • В темной — темно-серый текст на темно-бордовом фоне, контраст почти нулевой
  • При включенной в системе повышенной контрастности проблема остается: пара не меняется, потому что она собрана вручную
Почему

Каждому фоновому слоту схемы соответствует свой on-цвет, подобранный по контрасту (раздел 02). onSurface рассчитан на surface, а не на errorContainer.

Как надо
Surface(color = MaterialTheme.colorScheme.errorContainer) {
    Text(text = "Не хватает бонусов", modifier = Modifier.padding(16.dp))
}   // Surface сам подставит onErrorContainer через contentColorFor
ПравилоВзял фон из схемы — не указывай цвет текста вообще. Нужен оттенок потише — бери onSurfaceVariant только на поверхностях группы surface.

Кейс 3. Material You съел фирменный цвет

Включили динамические цвета — «так современнее и как в системных приложениях».

Как пишут
@Composable
fun AppTheme(
    darkTheme: Boolean = isSystemInDarkTheme(),
    dynamicColor: Boolean = true,                  // включено по умолчанию
    content: @Composable () -> Unit
) {
    val colorScheme = when {
        dynamicColor && Build.VERSION.SDK_INT >= Build.VERSION_CODES.S -> {
            val context = LocalContext.current
            if (darkTheme) dynamicDarkColorScheme(context) else dynamicLightColorScheme(context)
        }
        darkTheme -> DarkColors
        else -> LightColors
    }
    MaterialTheme(colorScheme = colorScheme, content = content)
}
Что видит пользователь
  • У пользователя с зелеными обоями приложение зеленое
  • Фирменный фиолетовый исчез: кнопки, ссылки, активные вкладки — все чужого цвета
  • Скриншоты в поддержке не совпадают с тем, что видит оператор
  • Маркетинг приносит макеты с брендом, а воспроизвести их нельзя
Почему

Динамическая схема строится из обоев и заменяет палитру целиком, включая primary. Для приложения без сильного бренда это плюс, для брендового — потеря узнаваемости.

Как надо
// вариант 1: бренд важнее — динамику не включаем
MaterialTheme(colorScheme = if (darkTheme) DarkColors else LightColors, content = content)

// вариант 2: динамика как настройка пользователя, по умолчанию выключена
@Composable
fun AppTheme(
    darkTheme: Boolean = isSystemInDarkTheme(),
    dynamicColor: Boolean = false,                 // осознанный выбор, а не дефолт шаблона
    content: @Composable () -> Unit
) { … }
ПравилоДинамические цвета — продуктовое решение, а не техническая деталь. Шаблон Android Studio включает их по умолчанию: это надо заметить и решить осознанно.

Кейс 4. Экран внезапно фиолетовый

Новый блок показывается в диалоге, который открывается из XML-экрана через ComposeView.

Как пишут
composeView.setContent {
    PromoBanner(promo = promo)        // темы нет
}
Что видит пользователь
  • Основные экраны выглядят правильно
  • Один блок нарисован фиолетовым: кнопка, ссылки и акценты не из палитры приложения
  • Шрифт тоже чужой: заголовок крупнее, чем везде
  • В темной теме блок остается светлым
Почему

Тема действует на поддерево композиции (раздел 01). Каждая точка входа — свой setContent, диалог, ComposeView в списке — начинает новое дерево, и если тему туда не положили, берется схема Material по умолчанию. Она фиолетовая, и это самый узнаваемый симптом.

Как надо
composeView.setContent {
    AppTheme {                        // тема в каждой точке входа
        PromoBanner(promo = promo)
    }
}

Чтобы не забывать, точку входа заворачивают один раз в свою функцию:

fun ComposeView.setThemedContent(content: @Composable () -> Unit) {
    setViewCompositionStrategy(ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed)
    setContent { AppTheme(content = content) }
}
ПравилоФиолетовый на экране — почти всегда «композиция без темы», а не ошибка палитры.

Кейс 5. Свой цвет положили в чужой слот

Нужен зеленый цвет успеха: галочка, статус «оплачено», подтверждение.

Как пишут
private val LightColors = lightColorScheme(
    primary = BrandPurple,
    tertiary = SuccessGreen        // «свободный слот, пусть будет успехом»
)

// на экране
Icon(imageVector = Icons.Default.Check, tint = MaterialTheme.colorScheme.tertiary)
Что видит пользователь
  • Галочка зеленая, все работает
  • Через месяц FilterChip в другом месте тоже стал зеленым: компоненты Material сами берут tertiary для акцентов
  • Дизайнер просит сделать акцент чипов синим — и ломает этим все статусы «оплачено»
Почему

Слоты схемы — это роли с назначением, а не свободные ячейки. tertiary используют готовые компоненты, и его смысл нельзя переопределить локально.

Как надо
@Immutable
data class AppColors(val success: Color, val onSuccess: Color, val warning: Color)

val LocalAppColors = staticCompositionLocalOf<AppColors> { error("AppColors not provided") }

@Composable
fun AppTheme(darkTheme: Boolean = isSystemInDarkTheme(), content: @Composable () -> Unit) {
    CompositionLocalProvider(LocalAppColors provides if (darkTheme) DarkAppColors else LightAppColors) {
        MaterialTheme(colorScheme = if (darkTheme) DarkColors else LightColors, content = content)
    }
}

// на экране
Icon(imageVector = Icons.Default.Check, tint = AppTheme.colors.success)
ПравилоНет слота для понятия — тему расширяют своим CompositionLocal, а не переосмысляют существующую роль.

Кейс 6. Переключатель темы в настройках не работает

В приложении три варианта: светлая, темная, как в системе.

Как пишут
// где-то в настройках
prefs.themeMode = ThemeMode.DARK        // записали и все

// в Activity
setContent {
    AppTheme(darkTheme = prefs.themeMode == ThemeMode.DARK) {
        AppNavHost()
    }
}
Что видит пользователь
  • Выбрал темную тему в настройках
  • Ничего не изменилось, пока приложение не перезапустишь
  • После перезапуска тема применилась — пользователь думает, что так и задумано
Почему

prefs.themeMode — обычное значение, а не состояние: Compose не знает, что оно изменилось, и перечитывать его некому. Тема обязана приходить из наблюдаемого источника.

Как надо
// репозиторий настроек отдает поток
val themeMode: StateFlow<ThemeMode> = settingsRepository.themeMode
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), ThemeMode.SYSTEM)

// Activity
setContent {
    val themeMode by viewModel.themeMode.collectAsStateWithLifecycle()
    val darkTheme = when (themeMode) {
        ThemeMode.LIGHT -> false
        ThemeMode.DARK -> true
        ThemeMode.SYSTEM -> isSystemInDarkTheme()
    }

    AppTheme(darkTheme = darkTheme) {
        AppNavHost()
    }
}
Побочный эффект

Смена темы перезапускает все поддерево — она объявлена через staticCompositionLocalOf (раздел 07). Это нормально: событие редкое. Но именно поэтому в тему не кладут часто меняющиеся значения.

ПравилоТема — это состояние приложения. Читается из потока, а не из prefs напрямую.

Кейс 7. Размеры шрифта заданы руками

По макету заголовок 20, подпись 13 — проставили как есть.

Как пишут
Text(text = gift.title, fontSize = 20.dp.value.sp, fontWeight = FontWeight.Bold)
Text(text = gift.subtitle, fontSize = 13.sp, color = Color.Gray)
Text(text = gift.price, style = TextStyle(fontSize = 15.sp))
Что видит пользователь
  • На стандартных настройках верстка совпадает с макетом
  • У пользователя с увеличенным системным шрифтом часть текста осталась мелкой — там, где размер пришел в dp
  • Заголовки в разных экранах отличаются на пару пунктов: числа проставляли по разным макетам
  • Смена шрифта дизайн-системы требует правки сотни мест
Почему

Типографика — такая же система, как палитра (раздел 04). Числа в экранном коде выпадают из нее ровно так же, как литералы цвета. Отдельно про единицы: sp масштабируется системной настройкой, dp — нет.

Как надо
Text(text = gift.title, style = MaterialTheme.typography.headlineSmall)
Text(
    text = gift.subtitle,
    style = MaterialTheme.typography.bodySmall,
    color = MaterialTheme.colorScheme.onSurfaceVariant
)
Text(text = gift.price, style = MaterialTheme.typography.titleMedium)

Проверяется превью с fontScale = 2f (раздел 08): на нем сразу видно и незамасштабированный текст, и блоки, которые от увеличения разваливаются.

ПравилоРазмер и начертание берутся из typography. В экранном коде остаются только color и maxLines.

Кейс 8. В темной теме карточки слились с фоном

Список карточек, каждая отделена тенью — как в Material 2.

Как пишут
Card(
    colors = CardDefaults.cardColors(containerColor = MaterialTheme.colorScheme.surface),
    elevation = CardDefaults.cardElevation(defaultElevation = 4.dp)   // отделяем тенью
) { … }
Что видит пользователь
  • В светлой теме карточки видно: тень дает границу
  • В темной карточки сливаются с фоном в сплошное полотно — тень на темном не читается
  • Границы блоков приходится угадывать по отступам между текстом
Почему

Тень — прием светлой темы: она работает, когда есть что затемнять. В Material 3 слои различают цветом: шкала surfaceContainer* (раздел 02) для того и сделана. Эти слоты не зависят от tonalElevation — они просто разные цвета в схеме, и в темной теме разница между ними видна.

Как надо
Card(
    colors = CardDefaults.cardColors(
        containerColor = MaterialTheme.colorScheme.surfaceContainer   // слой задан цветом
    ),
    elevation = CardDefaults.cardElevation(defaultElevation = 0.dp)
) { … }

// карточка внутри карточки — следующая ступень шкалы
Card(colors = CardDefaults.cardColors(MaterialTheme.colorScheme.surfaceContainerHigh)) { … }
ПравилоСлои различают слотами шкалы поверхностей. Тень остается для того, что действительно висит над контентом: FAB, шторка, диалог.

Чеклист ревью

  1. В экранном коде нет Color(0x…), fontSize, литеральных радиусов.
  2. Фон взят из схемы — цвет текста не указан вовсе.
  3. Каждая точка входа в композицию завернута в тему.
  4. Свои токены живут в собственном CompositionLocal, а не в слотах Material.
  5. Класс своих токенов помечен @Immutable.
  6. Тема приходит из наблюдаемого состояния, а не из prefs.
  7. Слои отделены слотами surfaceContainer*, тень — только для плавающего.
  8. У компонента есть превью в трех вариантах: светлая, темная, fontScale = 2f.
Итог

Тема — это не набор констант, а три системы (в Expressive — четыре), разложенные по дереву композиции. Компонент не знает своих цветов: он знает роли и читает их из ближайшей темы. Поэтому все ошибки этой темы одинаковы по форме — значение, которое выпало из системы: литерал цвета, число кегля, чужая пара, композиция без темы.
